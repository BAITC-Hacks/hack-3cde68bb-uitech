# uitech — инструкции для работы с проектом

## Контекст

- HackAlem AI, направление «Логистика». Команда: Rajan (пользователь, Java-разработчик) и Altynbek (аналитик, менеджер).
- ТЗ получено: автоматический расчёт заказов поставщикам для пополнения склада, постановщик — «Электрокомплект». Анализ и план: `docs/ANALYSIS_PLAN.md`, аудит источников: `docs/DATA_AUDIT.md`.
- Обязательны: учёт всех входных источников, сезонности и устойчивого роста, компенсация подтверждённого stockout, исключение разовых крупных заказов, группировка рекомендаций по поставщикам и объяснение количества. Не придумывай отсутствующие данные или критерии оценки.
- До официального старта готовим инструменты, инструкции и общие технические заготовки. Основную функциональность задачи разрабатываем в соревновательный период.
- Основная разработка и история изменений должны находиться в этом репозитории организатора: `BAITC-Hacks/hack-3cde68bb-uitech`. Родительская папка содержит отдельный репозиторий подготовки.

## Предлагаемая структура

- `backend/` — Java 17 / Spring Boot: расчёт, API, импорт Systeme Electric и IEK, PostgreSQL/Flyway и локальный FileStorage. Команды — в локальном AGENTS.md и README.
- `frontend/` — отдельное приложение React / TypeScript / Vite: импорт, рекомендации, графики, корректировка, утверждение и экспорт.
- `ai-agent/` — необязательное приложение. Создавай его при обоснованной потребности в отдельных зависимостях или процессе. Простые обращения к модели могут оставаться в backend.
- `docs/` — ТЗ, описание API и другие общие материалы.
- `README.md` — установка, настройка, запуск и проверка всего решения.
- Backend и frontend реализованы; ai-agent пока не нужен. Все приложения ведём в одном Git-репозитории, без вложенных репозиториев.

## Область инструкций

- Этот файл содержит общие правила проекта.
- Перед изменением компонента прочитай его локальный `AGENTS.md`, если он существует, включая применимые инструкции в промежуточных каталогах.
- В локальные файлы добавляй только особенности компонента: выбранный стек, фактические команды запуска и проверок, соглашения по коду. Не копируй общие правила.
- Поддерживай инструкции короткими и актуальными. Не записывай в них секреты и не выдавай планируемые команды за проверенные.

## Реализация и интеграция

- Приоритет: обязательные требования ТЗ, работающий сквозной сценарий, надёжный запуск, затем дополнительные функции и оформление.
- Выбирай минимальную достаточную архитектуру. Новые сервисы, базы данных и инфраструктуру добавляй для конкретной потребности задачи.
- Интерфейсы компонентов зафиксированы в `docs/api-contract.md`: endpoints, поля, типы, единицы измерения и ошибки. Контрольные сценарии — `docs/ACCEPTANCE_CASES.md`, синтетические входы — `fixtures/contract/`.
- При изменении API обновляй описание и затронутые клиентские вызовы вместе.
- Проверяй входные данные, числовые ограничения и вычисления кодом. Ответ модели не является доказательством правильности расчёта.
- Обрабатывай ошибки и таймауты внешних сервисов. Демонстрационные данные и заглушки должны быть явно обозначены.
- Храни секреты в переменных окружения; в примерах конфигурации оставляй только имена и безопасные значения-заполнители.

## Проверка и сдача

- Выполняй проверки, соответствующие изменениям. Для ключевой логики проверяй обычный случай, ограничения и ошибочные входные данные.
- Проверяй полный сценарий: входные данные → обработка → отображение результата. Перед сдачей воспроизведи запуск по README в чистой среде или на втором ноутбуке.
- README должен содержать назначение, архитектуру, технологии, зависимости, установку, переменные окружения, запуск и способ проверки основного сценария.
- Предусмотри проверку ключевой функциональности экспертами без личных аккаунтов команды согласно требованиям организатора. Заглушка не заменяет такую проверку.
- Раскрывай сторонние библиотеки, модели, данные, шаблоны и подготовленные до старта компоненты: источник, версия при наличии, лицензия или условия использования.
- Отделяй измеренные результаты от предположений. Сообщай, какие проверки действительно выполнены и что осталось непроверенным.
- Во время соревнования сохраняй подтверждаемый прогресс каждый час. По имеющемуся положению итоговая отсечка — 23 сентября 2026 года, 18:00 по Астане; сверяй официальные объявления и инструкции подачи.
- Изменения после отсечки не выдавай за сданную версию. Сохрани идентификатор финального коммита и подтверждение подачи.
