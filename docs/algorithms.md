# SupplyMind — алгоритмы расчёта заказов поставщикам

Документ описывает текущий `replenishment_v1`. Предложения по развитию отмечены отдельно и не являются реализованными функциями. Бизнес-процесс: [business_process.md](business_process.md), точные поля API: [api-contract.md](api-contract.md), контрольные примеры: [ACCEPTANCE_CASES.md](ACCEPTANCE_CASES.md).

## 1. Реализованный pipeline

```text
Известные XLSX-шаблоны / нормализованный JSON
  -> mapping, нормализация и валидация
  -> выбор товара, склада и периода
  -> проверка полноты продаж, наличия, остатка и транзита
  -> профиль сезонности и исключение разовых крупных заказов
  -> базовая скорость по дням наличия
  -> сезонность и тренд / заданный прирост
  -> прогноз спроса и страховой запас
  -> потребность с учётом остатка и датированных поставок
  -> перевод единиц, MOQ, кратность
  -> дневной прогноз наличия и срочность
  -> числовое объяснение и группировка по поставщику
```

Упущенный спрос за заданные дни отсутствия сохраняется в истории. Он не прибавляется повторно к прогнозу: компенсация уже учтена через скорость продаж по дням наличия.

## 2. Нормализация

В адаптерах IEK и Systeme Electric код товара связывается с `sku_1c`. Внутренний `product_id` имеет вид `<поставщик>:<код>`. Коды остаются строками; ведущие нули сохраняются. Сопоставление выполняется внутри поставщика, без автоматического объединения с товаром другого поставщика.

Основные поля: `product_id`, `sku_1c`, `supplier_id`, `supplier_article`, `name`, `warehouse_id`, `date`, `quantity`, `operation_type`, `customer_id`, `document_id`, `free_stock_qty`, `expected_date`, `moq_purchase_qty`, `pack_multiple_purchase_qty`, `purchase_unit_factor`, `category_id`. Они принадлежат разным сущностям, а не одной плоской таблице; полная схема приведена в контракте.

Поставщика выбирает пользователь. Адаптеры поддерживают конкретные роли и шаблоны файлов, не произвольный Excel. Месячные сводки сохраняются и используются для сверки; `monthly_sales` и `monthly_stock` напрямую в расчётное ядро не входят. Их объединение с детализацией требует подтверждения периода, склада и отсутствия двойного учёта.

## 3. Валидация транзакций

Проверяются обязательные поля, идентификаторы, даты, количества, связи и типы операций. Текущие XLSX-адаптеры принимают положительные количества расходных накладных с необходимыми реквизитами. Отрицательные, нулевые, неполные и неподдерживаемые операции исключаются из принятой истории с замечанием и ссылкой на источник; `abs()` безусловно не применяется. Возврат в нормализованной истории блокирует расчёт с `RETURN_POLICY_REQUIRED`.

**Предложение по развитию:** после согласования семантики конкретного источника поддержать продажи с отрицательным знаком и отдельную политику возвратов/корректировок. Нельзя превращать возврат в продажу только по знаку количества.

## 4. Область расчёта и полнота данных

Расчёт разделён по `product_id + warehouse_id`. История берётся из `[history_start, as_of)`. Требуются покрытие продаж и состояние наличия каждого дня, остаток на дату расчёта, полнота транзита, единицы и правила закупки, политики поставщика и категории.

Неизвестные обязательные сведения дают `NEEDS_INPUT`, а не нулевой спрос или заказ. Поддерживаемые допущения задаются явно, с причиной и автором, и сохраняются в результате. Допущения отмечаются статусом `ASSUMED` для разрешённой к закупке готовой позиции.

## 5. Разовые крупные заказы

**Реализовано:** `robust_orders_v1`. Внутри товара и склада продажи группируются по дате и накладной; при наличии `customer_id` дополнительно проверяется сумма покупок клиента за день. Количество делится на сезонный коэффициент месяца.

При наличии не менее 8 агрегированных заказов рассчитываются медиана и MAD:

```text
threshold = max(3 * median, median + 3.5 * MAD / 0.67448975)
candidate = normalized_order_qty > threshold
```

Кандидат сохраняется как регулярная покупка, если сопоставимые объёмы от половины до двойного его количества встречались как минимум в трёх разных неделях. При известном клиенте проверяется его история; без ID клиента консервативно проверяется повторяемость на уровне SKU. Привязка к клиенту без идентификатора не выдумывается.

Исключённые события записываются в `anomalies`, исходные и очищенные продажи сохраняются раздельно. При недостаточной истории автоматическое исключение не выполняется; результат содержит предупреждение. При MAD = 0 остаётся порог `3 * median`.

**Предложения по развитию:** сравнить IQR, rolling median, анализ концентрации и явную проверку возвращения к обычному спросу после всплеска. Эти дополнительные методы пока не реализованы. Иллюстрации для будущей проверки, а не достаточные входы текущего детектора:

```text
Разовый всплеск: 10 11 12 500 10 11
Рост:           10 12 15 20 30 40 50
```

## 6. Компенсация stockout

**Реализован режим `confirmed_only`:** используется заданный календарь наличия. Неизвестный день блокирует расчёт, если нет явного `ASSUME_AVAILABLE`. Это допущение считает день доступным и не оценивает пропущенные stockout.

```text
base_daily_rate =
  sum(regular_sales(day) / seasonality(month(day)), по дням наличия)
  / число дней наличия

estimated_lost_qty(day) =
  base_daily_rate * seasonality(month(day)), если день отмечен stockout
  0, иначе
```

Без дней наличия расчёт блокируется. Оценка исторического упущенного спроса использует базовый уровень и сезонность; отдельной поправки на исторический тренд в ней нет. Будущий прогноз использует режим роста из раздела 7.

**Предложение по развитию, не реализовано:** выявлять вероятные периоды отсутствия по месячным остаткам, падению продаж и соседним периодам:

```text
low/zero monthly stock + sales drop + demand before/after
  -> estimated stockout с явно указанной неопределённостью
  -> estimated lost demand = max(0, expected demand - observed sales)
  -> corrected demand = observed sales + estimated lost demand
```

Нужно ограничить оценку доступной на дату прогноза историей, проверить влияние сезонности/тренда и не выдавать оценочную длительность за подтверждённые дни. ТЗ проверяет компенсацию зафиксированного stockout; восстановление отсутствия по месячным данным — дополнительный метод.

## 7. Прогноз: уровень, сезонность, рост

Сезонность имеет два режима:

- `provided`: выбор предоставленного профиля в порядке SKU → категория → поставщик. Применимость профиля требует подтверждения пользователем/партнёром.
- `estimate`: после предварительной очистки от разовых заказов оцениваются месячные дневные скорости SKU. Для каждого календарного месяца нужны минимум два полных месячных периода с не менее чем 14 днями наличия в каждом. Средние скорости нормируются на среднее по 12 месяцам; нулевые месячные скорости не допускаются. При недостатке данных возвращается `INSUFFICIENT_SEASONAL_HISTORY`, автоматического перехода к профилю категории/поставщика нет.

После определения профиля выполняется итоговая проверка выбросов. Рост задаётся одним из способов:

- `manual`: базовая скорость умножается на `1 + manual_growth_pct / 100`.
- `historical`: линейная регрессия по очищенным от сезонности месячным дневным скоростям. Требуются минимум три полных месяца; каждый должен иметь не менее `max(7, число_дней_месяца / 2)` дней наличия с целочисленным делением. Отрицательный прогноз уровня ограничивается нулём.

Дневной прогноз равен уровню выбранного режима, умноженному на сезонный коэффициент месяца. Это детерминированная модель, без Holt-Winters и Exponential Smoothing.

**Предложения по развитию:** сравнить Holt-Winters / Exponential Smoothing с текущей моделью и baseline; добавить проверенный fallback из `estimate` на профиль категории/поставщика. До проверки не заявлять улучшение точности.

## 8. Backtesting — план

Исторический backtest и сравнение качества моделей пока не выполнены. Функциональные тесты не измеряют точность на данных компании.

Предлагается walk-forward без случайного перемешивания:

```text
TRAIN -> следующий период TEST
TRAIN + предыдущий период -> следующий TEST
```

Сравнивать naive, seasonal naive и основную модель; считать MAE, WAPE, RMSE и Forecast Bias на сопоставимых наблюдаемых периодах. При нулевой сумме факта WAPE не определён. Настройки, профили и очистка для каждого среза должны использовать только информацию, доступную до тестового периода. Профили поставщика, содержащие более поздние данные или прогнозы, нельзя переносить в ранние срезы как известный факт.

## 9. Прогноз наличия по дням

Поступления учитываются перед спросом дня:

```text
available(t) = projected_stock(t-1) + confirmed_arrivals(t)
unmet_demand(t) = max(0, forecast_demand(t) - available(t))
projected_stock(t) = max(0, available(t) - forecast_demand(t))
```

Начальное значение — свободный остаток на дату расчёта. Неудовлетворённый спрос сохраняется отдельно; отрицательный остаток и перенос задолженности покупателей не моделируются. Новый рекомендуемый заказ ещё не считается размещённой поставкой. Позднее поступление не отменяет ранний дефицит.

## 10. Базовая потребность и страховой запас

```text
H = lead_time_days + review_period_days
end = as_of + H
forecast_horizon_qty = сумма прогноза за [as_of, end)
safety_stock_qty = сумма прогноза за [end, end + safety_days)
eligible_inbound_qty = сумма подтверждённых поставок за [as_of, end)

raw_order_stock_qty = max(0,
  forecast_horizon_qty + safety_stock_qty
  - free_stock_qty - eligible_inbound_qty)
```

Поставки требуют корректных дат, статуса, склада и подтверждения полноты; просроченные поставки требуют уточнения. Поставка ровно на `end` не входит в расчёт количества.

Срок поставки и период пересмотра задаются политикой поставщика, `safety_days` — политикой категории. Эти параметры требуют бизнес-согласования. Свободный остаток повторно не уменьшается на резерв. Прогнозный остаток на конец горизонта нельзя подставлять вместо `free_stock_qty + eligible_inbound_qty`: из него спрос уже вычтен, что привело бы к двойному учёту.

## 11. MOQ, кратность и единицы

Количество переводится из единиц хранения в единицы закупки. Минимальная партия и кратность — разные поля:

```text
Если raw_order_stock_qty = 0: recommended_purchase_qty = 0
Иначе:
  need_purchase = raw_order_stock_qty / purchase_unit_factor
  recommended_purchase_qty =
    ceil(max(need_purchase, moq_purchase_qty) / pack_multiple_purchase_qty)
    * pack_multiple_purchase_qty

recommended_stock_qty = recommended_purchase_qty * purchase_unit_factor
```

При запрете закупки политикой категории рекомендация равна нулю, статус — `EXCLUDED_BY_POLICY`. После ручной корректировки `final_purchase_qty` может отличаться от рекомендации; положительное количество должно соблюдать MOQ и кратность, причина обязательна.

Пример: потребность 347 шт., коэффициент 1, MOQ 100 шт., кратность 100 шт. → 400 шт. При кратности 1 шт. с тем же MOQ → 347 шт. Одно поле исходного файла нельзя автоматически интерпретировать одновременно как MOQ и кратность.

## 12. Риск дефицита

`first_stockout_date` — первый день с `unmet_demand_qty > 0`. Нулевой остаток после полного удовлетворения спроса сам по себе ещё не означает дефицит в этот день.

Дата сравнения — более ранняя из ближайшей существующей поставки и `as_of + lead_time_days`; если транзита нет, используется срок нового заказа. Срочность:

- `NORMAL`: дефицит внутри горизонта не прогнозируется.
- `BEFORE_NEXT_DELIVERY`: первый дефицит раньше даты сравнения.
- `WITHIN_HORIZON`: дефицит есть, но не раньше даты сравнения.
- `UNKNOWN`: расчёт заблокирован.

Это заданная методология MVP; её применимость требует бизнес-проверки. Предложение `Days of Stock = Current Stock / Expected Daily Demand` можно использовать как дополнительный индикатор при положительном дневном спросе, но сейчас оно не определяет срочность.

## 13. Объяснение расчёта

Результат сохраняет параметры методологии, факторы, историю, прогноз по дням, аномалии, предупреждения, допущения и ссылки на источники. Текст объяснения строится из чисел расчёта.

Синтетический арифметический пример, фрагмент полей результата, не полный ответ API:

```json
{
  "sku_1c": "A-101",
  "factors": {
    "forecast_horizon_qty": 600,
    "safety_stock_qty": 97,
    "free_stock_qty": 200,
    "eligible_inbound_qty": 150,
    "raw_order_stock_qty": 347
  },
  "recommended_purchase_qty": 400,
  "recommended_stock_qty": 400,
  "final_purchase_qty": 400
}
```

Здесь `600 + 97 - 200 - 150 = 347`; коэффициент единиц равен 1, MOQ и кратность равны 100. Правила закупки находятся в товаре; числа выбраны для иллюстрации арифметики, а не измерены на реальном SKU. Ближайшая дата поступления отдельным полем рекомендации пока не выводится — это предложение по развитию.

## 14. Группировка и решение менеджера

Рекомендации группируются по `supplier_id`. Менеджер меняет количество с причиной, затем утверждает весь расчёт конкретной версии. Позиция с нулевым итоговым количеством не попадает в CSV. Отдельных статусов принятия/отклонения строки нет; `NEEDS_INPUT` блокирует утверждение и не допускает ручного обнуления для обхода проверки.

Изменение количества снимает утверждение. CSV выгружается по поставщику только для актуальной утверждённой версии. Совместимость формата с учётной системой компании ещё нужно проверить. Отправка поставщику не реализована.

## 15. Must-have проверки

Контрольные сценарии и ожидаемые числа приведены в [ACCEPTANCE_CASES.md](ACCEPTANCE_CASES.md). Это синтетические проверки поведения, не измерение качества на данных компании.

| Требование | Текущая проверка |
|---|---|
| Влияние входов | Продажи, остаток, транзит, категория и заданный прирост меняют потребность в примерах без насыщения нулём |
| Сезонность и рост | Предоставленный профиль сохраняет пик; устойчивый рост повышает прогноз; режим estimate отдельно проверяется на требования к истории |
| Stockout | Заданные дни отсутствия повышают расчётный спрос относительно сырых продаж; неизвестное наличие не становится фактом отсутствия |
| Разовые крупные заказы | Всплеск и дробление заказа одного клиента не искажают регулярный прогноз сверх допуска контрольного примера; повторяющиеся крупные покупки сохраняются |
| Итоговый список | Группировка по поставщику и числовое объяснение готовых строк |

Инженерный допуск контрольного примера — не критерий организатора. Проверка автоматического восстановления stockout по месячным данным будет нужна при реализации этого метода.

## 16. Дополнительные проверки и ограничения

- Даты транзита должны влиять на ранний дефицит; перенос за границу горизонта меняет учтённое количество. Не любое изменение даты обязано менять срочность.
- MOQ/кратность могут менять округлённый заказ, сохраняя исходную потребность; при нулевой потребности заказ остаётся нулевым.
- Один код из разных файлов одного поставщика связывается с одним `product_id`; проверяются конфликты, единицы и ссылки на источник.
- Возврат не превращается в продажу из-за безусловного `abs()`; неподдержанная политика блокирует расчёт.
- Наличие реального файла в хранилище не означает подтверждение полноты его бизнес-содержимого. Неполные выгрузки могут импортироваться со статусом `PARTIAL` и требовать уточнений до расчёта.

## 17. Архитектура MVP

```text
IEK XLSX / Systeme Electric XLSX / нормализованный JSON
  -> Java: адаптеры импорта и общая модель
  -> PostgreSQL: данные, расчёты, версии, аудит
     + локальный FileStorage: оригиналы файлов
  -> Java: детерминированное расчётное ядро
  -> REST API
  -> React: качество данных, настройки, рекомендации, карточка SKU
  -> ручная корректировка и утверждение
  -> CSV
```

**План развития:** оценочный stockout по месячным данным, исторический backtest, сравнение моделей, проверенный сезонный fallback, ближайшая поставка в рекомендации, отдельные решения по строкам и согласованный формат интеграции с учётной системой. Прямой обмен с 1С и универсальные адаптеры других источников пока не реализованы.
