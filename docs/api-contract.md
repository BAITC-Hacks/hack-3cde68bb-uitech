# Контракт данных и API v1

Статус: реализованный backend API v1. Frontend ещё не реализован. Поля и правила ниже — решения команды, а не дополнительные требования организаторов. Адаптер XLSX пока поддерживает только Systeme Electric.

## 1. Общие соглашения

- Базовый путь: `/api/v1`. JSON UTF-8, имена полей `snake_case`.
- Идентификаторы — строки. Коды 1С не преобразуются в числа. `product_id` — уникальный ID товара внутри набора; `supplier_id + sku_1c` — уникальная пара.
- Количества — конечные JSON-числа, не строки и не NaN. Backend считает количества и округление десятичной арифметикой. В JSON не передавать числа больше безопасного диапазона JS.
- Даты: `YYYY-MM-DD`; временные отметки ответа — ISO 8601 со смещением. Для набора явно задаётся `timezone`.
- `as_of` означает состояние **на начало указанного дня**. История обучения заканчивается до этой даты. Конец интервалов `start_date/end_date_exclusive` не включается. Это исключает двойной учёт последнего дня.
- Горизонт прогноза: `[as_of, as_of + lead_time_days + review_period_days)`. Поставка в последний включённый день учитывается, на дату исключённой границы — нет. Получение происходит в начале дня, потребление — в течение дня.
- `null` означает «неизвестно». Пустое поле/ячейка не становится нулём без явно принятой политики импорта. Неизвестная рекомендация возвращается как `null`, не как 0.
- Исходные Excel-файлы не изменять. Все синтетические примеры помечены `data_kind: synthetic` и не смешиваются с фактическими наборами.

## 2. Нормализованный набор

`POST /datasets` принимает следующий объект. Он служит также форматом контрольных примеров.

```json
{
  "schema_version": "1.0",
  "name": "Контрольный пример",
  "data_kind": "synthetic",
  "timezone": "Asia/Almaty",
  "suppliers": [],
  "products": [],
  "sales_coverage": [],
  "sales": [],
  "inventory": [],
  "inbound": [],
  "inbound_coverage": [],
  "availability": [],
  "seasonality_profiles": [],
  "sources": [],
  "issues": []
}
```

| Массив | Поля одной записи |
|---|---|
| `suppliers` | `supplier_id`, `name` |
| `products` | `product_id`, `supplier_id`, `sku_1c`, `supplier_article` (nullable), `name`, `stock_unit`, `purchase_unit`, `purchase_unit_factor`, `category_id` (nullable), `moq_purchase_qty` (nullable), `pack_multiple_purchase_qty` (nullable), `source_refs` |
| `sales_coverage` | `product_id`, `warehouse_id`, `start_date`, `end_date_exclusive`, `complete` |
| `sales` | `sale_id`, `product_id`, `warehouse_id`, `date`, `document_id`, `customer_id` (nullable, только обезличенный), `operation_type`, `quantity`, `source_refs` |
| `inventory` | `product_id`, `warehouse_id`, `as_of`, `free_stock_qty` (nullable), `source_refs` |
| `inbound` | `shipment_id`, `product_id`, `warehouse_id`, `quantity`, `expected_date` (nullable), `status: confirmed/unconfirmed`, `source_refs` |
| `inbound_coverage` | `product_id`, `warehouse_id`, `as_of`, `complete` — подтверждает полноту списка открытых поставок на дату |
| `availability` | `product_id`, `warehouse_id`, `start_date`, `end_date_exclusive`, `state: available/stockout/unknown`, `provenance: observed/manual/synthetic`, `source_refs` |
| `seasonality_profiles` | `profile_id`, `scope_type: product/category/supplier`, `scope_id`, `basis: daily_rate`, `indices` (12 чисел, январь–декабрь), `source_refs` |
| `sources` | `source_id`, `kind: xlsx/manual/synthetic`, `role`, `file_name` (nullable), `note` |
| `issues` | `code`, `severity: info/warning/error`, `product_id` (nullable), `message`, `source_refs` |
| `monthly_sales`, `monthly_stock` | Необязательные массивы: `product_id`, `warehouse_id`, `month: YYYY-MM`, `quantity` (nullable, исходный знак сохраняется), `meaning`, `source_refs` |

`source_refs` — массив `{source_id, sheet, cell_range}`; `sheet` и `cell_range` могут быть null для ручного или синтетического источника. Не передавать абсолютные пути компьютера через пользовательский API.

### Значения и проверки

- `purchase_unit_factor` — число единиц хранения в одной единице закупки, строго больше 0 либо null, если неизвестно. Например, 305 метров на бухту. Не выводить автоматически из названия без подтверждения. Null блокирует расчёт.
- В `sales` `quantity > 0`, а направление задаёт `operation_type: sale/return`. Неопознанные корректировки остаются в карантине импорта. Исходный знак хранится в журнале источника; он не меняется через `abs`.
- При наличии возвратов спрос не рассчитывать молча по модулю или сумме всех движений. Требуется выбранная политика возвратов; пока её нет, затронутые позиции получают `RETURN_POLICY_REQUIRED`. Возвраты не отменяют уже переданный снимок остатка.
- В `inventory` один снимок на товар, склад и дату. Адаптер вычисляет свободный остаток один раз из согласованного источника. Если источник уже содержит свободный остаток, резерв повторно не вычитать.
- В `inbound` количество выражено в единицах хранения. При неопределённой дате нельзя автоматически считать поставку своевременной. Отсутствие записей означает нулевой транзит только при подтверждённой полноте источника в отчёте импорта.
- Периоды наличия одного товара/склада не пересекаются. Stockout и продажа в один день — конфликт данных для упрощённой дневной модели.
- Полное покрытие продаж позволяет трактовать отсутствие события в конкретный день как нулевые продажи. Оно **не доказывает наличие товара** в этот день.
- Сезонные индексы — строго положительные относительные уровни дневного спроса, среднее по 12 месяцам равно 1. Профиль месячных объёмов адаптер сначала переводит в профиль дневной скорости с учётом длины месяца и документирует преобразование.
- Дубликаты ID, конфликтующие снимки и нарушенные внешние ключи — ошибки. Разные строки одной накладной допустимы и агрегируются по документу/товару/складу, а не удаляются как дубликаты.

## 3. Настройки расчёта

`POST /calculations`:

```json
{
  "dataset_id": "ds_example",
  "as_of": "2026-07-01",
  "warehouse_id": "WH_TEST",
  "supplier_ids": ["SUP_A"],
  "category_ids": [],
  "history_start": "2026-06-01",
  "supplier_policies": [
    {"supplier_id": "SUP_A", "lead_time_days": 7, "review_period_days": 7}
  ],
  "category_policies": [
    {"category_id": "STANDARD", "safety_days": 7, "purchasing_allowed": true}
  ],
  "forecast": {
    "seasonality_mode": "provided",
    "growth_mode": "manual",
    "manual_growth_pct": 0,
    "outlier_policy": "robust_orders_v1",
    "stockout_mode": "confirmed_only"
  },
  "assumptions": []
}
```

- Пустые `supplier_ids/category_ids` означают все значения. Пропущенные/null массивы нормализуются в пустые; предпочтительно передавать явно. Неизвестные значения фильтра возвращают 422.
- `lead_time_days >= 0`, `review_period_days >= 1`, `safety_days >= 0`, целые.
- `growth_mode: manual/historical`. `manual_growth_pct >= -100`, обязателен только для manual; при historical должен быть null. В v1 исключаем одновременное ручное и автоматическое применение одного тренда.
- `seasonality_mode: provided/estimate`. При provided выбирается один профиль: product → category → supplier. При estimate метод и область обучения сохраняются в результатах. Не применять два профиля последовательно.
- `robust_orders_v1` означает анализ документа и, если доступен, клиентского агрегата с учётом сезонности и повторяемости. Конкретные параметры детектора сохраняются в `methodology`, версия меняется при изменении поведения. Тесты ниже ограничивают ожидаемое поведение, не подменяют реализацию.
- Неизвестная категория не получает произвольную политику; требуется ручное сопоставление или явная настройка `UNCATEGORIZED` как допущение.
- Неизвестные наличие/транзит/остаток не скрывать. Для неполных данных допустим расчёт только по явному допущению с `code`, `scope_id`, `value`, `reason`, `accepted_by`. Факт и допущение сохраняются отдельно.
- Для товаров с недостаточной историей оценки тренда или всплесков возвращать предупреждение либо блокировку, а не выдуманную точность.

### Арифметика и единицы

Для плоского очищенного ряда с известным наличием базовая дневная скорость = продажи в дни наличия / число дней наличия. При сезонности перед усреднением снимается её влияние. Предполагаемый спрос в дни подтверждённого отсутствия выводится отдельно; нули этих дней не должны второй раз уменьшать базовую скорость.

`D_H` — сумма дневного прогноза за горизонт H. Для однозначной приёмки v1 `S` — сумма прогноза за следующие `safety_days` **после конца H**. `Q_raw_stock = max(0, D_H + S - free_stock - eligible_inbound)`.

Переводим потребность в единицы закупки: `Q_raw_purchase = Q_raw_stock / purchase_unit_factor`. При нулевой потребности заказ 0. Иначе:

`Q_purchase = ceil(max(Q_raw_purchase, MOQ_purchase) / pack_multiple_purchase) × pack_multiple_purchase`.

`Q_stock = Q_purchase × purchase_unit_factor`. Если MOQ/кратность/единицы неизвестны, возвращаем статус `NEEDS_INPUT`, количества null и пустые факторы расчёта; согласованное отсутствие ограничения записывается явно как MOQ=0, кратность согласно допустимой единице закупки.

Прогноз дефицита строится отдельно по датам с учётом **имеющихся** поставок, без фиктивного включения нового ещё не утверждённого заказа. Просроченные неполученные поставки не считать уже доступными.

## 4. Endpoints

| Метод и путь | Запрос | Успех |
|---|---|---|
| `GET /health` | — | 200 `{status: "ok", api_version: "1.0"}` |
| `POST /datasets` | Нормализованный JSON | 201, `DatasetSummary` |
| `POST /datasets/import` | Multipart: `manifest` JSON + файлы по именованным частям | 201, `DatasetSummary`; пока синхронный импорт |
| `GET /datasets/{id}` | — | 200, `DatasetSummary` |
| `GET /datasets/{id}/data` | — | 200, полный нормализованный набор, включая все issues и месячные значения |
| `POST /calculations` | Настройки выше | 201, `CalculationResult`, состояние DRAFT |
| `GET /calculations/{id}` | — | 200, актуальный результат |
| `GET /calculations/{id}/items/{item_id}` | — | 200, строка + история/прогноз/аномалии |
| `PATCH /calculations/{id}/items/{item_id}` | `expected_revision`, `final_purchase_qty` (null = сброс), `reason` | 200, обновлённый результат |
| `POST /calculations/{id}/approve` | `expected_revision`, `approved_by`, `acknowledged_issue_codes` | 200, утверждённая версия |
| `GET /calculations/{id}/export?supplier_id=…&format=csv&revision=…` | Нужна актуальная утверждённая версия | 200, скачиваемый CSV |

Новый расчёт создаёт новый ID и всегда DRAFT; старое утверждение относится только к старому снимку. Пересчёт не изменяет старый результат. Изменение количества существующего расчёта увеличивает `revision` и сбрасывает его утверждение. Два одновременных изменения проверяют `expected_revision`.

XLSX-экспорт можно добавить после CSV. Endpoint отправки заказа поставщику в v1 отсутствует. `approved_by` — введённое имя для локальной истории MVP, не доказанная аутентификация и не электронная подпись.

### Импорт файлов

Manifest содержит `name`, `data_kind: real`, `timezone`, `files: [{part_name, supplier_id, role}]`. Реализованный адаптер требует `supplier_id: SYSTEME` и ровно по одному файлу каждой из шести ролей: `sales_transactions`, `sales_monthly`, `stock_monthly`, `inventory_transit`, `moq`, `seasonality`. Копии месячной истории и ошибочные сводные формулы из транзитной таблицы не прибавляются к продажам. Пример клиента — `tools/import_systeme.py`.

API принимает XLSX: 15 МБ на файл, 40 МБ на multipart-запрос; превышение даёт 413. Клиентский Python-скрипт читает ZIP в памяти, проверяет шесть файлов, 15 МБ на файл и 35 МБ суммарно. Серверный ZIP-импорт отсутствует. Импорт синхронный; отдельного таймаута обработки сервер пока не задаёт. Повторный импорт того же нормализованного содержимого, имени и параметров возвращает прежний dataset (200, `reused: true`), новый — 201. Это также относится к POST /datasets. ID — SHA-256 нормализованного JSON.

`DatasetSummary`: `dataset_id`, `name`, `data_kind`, `schema_version`, `status: READY/PARTIAL`, `counts`, `sources`, `coverage`, `issues`, `created_at`. `coverage` отдельно отражает даты и область продаж, снимков, наличия, клиентов и транзита. `PARTIAL` не маскирует строки без количества; они отражаются в отчёте карантина.

Дополнительно: `issue_count`, `issues_truncated`, первые 200 issues; поле `reused` возвращается после POST. Статус набора — предварительная оценка, готовность каждой строки для конкретных дат определяется расчётом.

### Поддерживаемые допущения и ограничения адаптера

Каждое допущение: `{code, scope_id, value: true, reason, accepted_by}`. Область — product_id, supplier_id или `*`. Поддержаны:

- `ASSUME_AVAILABLE`: неизвестное дневное наличие считается наличием для сценария; история маркируется `assumed_available`. Подтверждённый stockout не переопределяется.
- `CONFIRM_SALES_COVERAGE`: признаёт полноту существующего интервала покрытия. Не добавляет отсутствующий интервал и не расширяет его даты.
- `CONFIRM_INBOUND_SCOPE`: подтверждает существующий источник транзита на точную дату. Не исправляет неизвестную дату или количество поставки.
- `CONFIRM_SNAPSHOT_SCOPE`: снимает соответствующий вопрос к области исходного снимка. Не меняет дату/количество и не создаёт отсутствующий остаток.
- `EXCLUDE_QUARANTINED_OPERATIONS`: явное согласие исключить операции из карантина. Они не преобразуются в положительные продажи.

Для полей, которые нельзя исправить допущением, нужен новый нормализованный dataset с подтверждёнными значениями и ручными source_refs. Импорт пока не даёт редактора бизнес-правил. `purchase_unit` предварительно повторяет единицу хранения, но `purchase_unit_factor` и MOQ остаются null до подтверждения. Месячные остатки имеют неизвестный момент измерения; из них не восстанавливаются даты stockout. Для сезонного профиля используются L11:L22 с нормализацией по длине месяцев 2025; допущение об интерпретации отмечается предупреждением.

Исторический тренд — линейная регрессия очищенной дневной скорости по полным месяцам: минимум три месяца, в каждом не меньше половины дней с известным наличием. Сезонная оценка требует минимум два полных наблюдения каждого месяца года, не менее 14 дней наличия в каждом; нулевой/недостаточный профиль блокируется. Параметры детектора: минимум 8 документов, порог больше max(3 × медиана, медиана + 3.5 × MAD / 0.67448975), повторяемость сравнимых покупок одного клиента в ≥3 неделях сохраняет событие. Без ID клиента повторяемость оценивается по документам товара, клиентская принадлежность не восстанавливается; ограничение отмечается предупреждением. Это эвристика, требующая оценки на реальных данных.

## 5. Ответ расчёта

```json
{
  "calculation_id": "calc_example",
  "dataset_id": "ds_example",
  "revision": 1,
  "status": "DRAFT",
  "data_kind": "synthetic",
  "as_of": "2026-07-01",
  "warehouse_id": "WH_TEST",
  "methodology": {"version": "replenishment_v1", "parameters": {}},
  "summary": {"supplier_count": 1, "item_count": 1, "needs_input_count": 0},
  "supplier_groups": [{"supplier_id": "SUP_A", "item_ids": ["item_P1"]}],
  "items": [{
    "item_id": "item_P1",
    "product_id": "P1",
    "supplier_id": "SUP_A",
    "sku_1c": "000001_",
    "name": "Контрольный товар",
    "stock_unit": "pcs",
    "purchase_unit": "pcs",
    "status": "READY",
    "urgency": "BEFORE_NEXT_DELIVERY",
    "first_stockout_date": "2026-07-05",
    "recommended_purchase_qty": 150,
    "recommended_stock_qty": 150,
    "final_purchase_qty": 150,
    "override": null,
    "factors": {
      "base_daily_rate": 10,
      "horizon_days": 14,
      "forecast_horizon_qty": 140,
      "safety_stock_qty": 70,
      "free_stock_qty": 40,
      "eligible_inbound_qty": 20,
      "raw_order_stock_qty": 150,
      "lost_demand_estimate_qty": 0,
      "excluded_sales_qty": 0
    },
    "explanation": "Спрос 140 + запас 70 − остаток 40 − поставки 20 = 150 шт.",
    "warnings": [],
    "assumptions": [],
    "source_refs": []
  }],
  "approval": null
}
```

Пример дефицита предполагает поступление 20 единиц на 8 июля, как в базовом fixture. С 1 по 4 июля остаток 40 покрывает четыре дня по 10, 5 июля возникает неудовлетворённый спрос. Нулевой остаток на конец 4 июля сам по себе ещё не означает потерянную продажу 4 июля.

`item.status`: `READY`, `ASSUMED`, `NEEDS_INPUT`, `EXCLUDED_BY_POLICY`. При блокирующей нехватке данных числовые поля, которые нельзя вычислить, — null. Для запрета закупки по подтверждённой категории количество 0, но неудовлетворённую потребность показываем отдельно.

`urgency`: `BEFORE_NEXT_DELIVERY`, `WITHIN_HORIZON`, `NORMAL`, `UNKNOWN`. Точное правило: первая дата дефицита раньше ближайшей подтверждённой поставки или ожидаемого прибытия нового заказа → BEFORE_NEXT_DELIVERY; иначе в H → WITHIN_HORIZON. Неполные даты → UNKNOWN.

Карточка дополнительно содержит `history: [{date, actual_sales_qty, regular_sales_qty, estimated_lost_qty, availability_state}]`, `forecast: [{date, demand_qty, projected_stock_qty, unmet_demand_qty}]`, `anomalies: [{document_ids, customer_id, date, original_qty, excluded_qty, reason, decision}]`. Даты при месячной истории сохраняют явно указанную гранулярность; месячные значения не выдавать за реальные дневные наблюдения.

Сумму единиц по метрам и штукам не выводить как общий KPI. Стоимость заказа не показывать без сопоставимых закупочных цен и валюты.

## 6. Ошибки, утверждение и экспорт

Ошибка: `{error: {code, message, fields: [{path, message}], request_id}}`. Структурно некорректный JSON/manifest — 400; неизвестный ID — 404; конфликт revision или неутверждённый экспорт — 409; некорректные значения/блокирующая попытка утверждения — 422; превышение объявленного лимита — 413. Не возвращать трассировки и секреты.

Валидный расчёт с неполными данными возвращает 201/200 и `NEEDS_INPUT` по затронутым строкам. Такой результат не утверждается, пока пользователь не предоставит данные. Политика запрета закупки даёт 0 только после успешной проверки входов и не обходит блокировки. Для отдельного набора поставщиков/категорий создаётся новый расчёт с фильтрами. При утверждении `acknowledged_issue_codes` должен включать все коды предупреждений и допущений результата, включая ограничения импорта.

Ручное количество неотрицательно, соответствует единице/кратности и минимуму, если положительно. Ноль допустим как осознанный отказ от заказа с причиной. Нельзя изменить `recommended_*` через PATCH: они сохраняют результат алгоритма. `override` хранит новое значение и причину; null сбрасывает к рекомендации.

CSV: UTF-8 с BOM, разделитель `;`, точка в десятичных числах, строки CRLF, текст экранируется по правилам CSV. Колонки: `supplier_id;sku_1c;supplier_article;name;warehouse_id;as_of;purchase_unit;recommended_purchase_qty;final_purchase_qty;reason`. Текст, начинающийся с формульных символов Excel, экранировать как текст. Коды должны оставаться строками при импорте в учётную систему. Сохранение типов в обычном CSV ограничено; для гарантированного открытия в Excel с ведущими нулями потребуется XLSX либо явная настройка импорта. Формат 1С ещё не подтверждён постановщиком.

Экспорт содержит только положительные окончательные количества выбранного поставщика и соответствует указанным `revision` и утверждению. Имя файла включает ID расчёта, поставщика и revision. Сетевых вызовов поставщику не выполняется.
