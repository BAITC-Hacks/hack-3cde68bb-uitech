# Контракт данных и API v1

Статус: реализованный backend API v1, подключён frontend React / TypeScript. Поля и правила ниже — решения команды, а не дополнительные требования организаторов. Адаптеры XLSX поддерживают Systeme Electric и IEK.

## 1. Общие соглашения

- Базовый путь: `/api/v1`. JSON UTF-8, имена полей `snake_case`.
- Идентификаторы — строки. Коды 1С не преобразуются в числа. `product_id` — уникальный ID товара внутри набора; `supplier_id + sku_1c` — уникальная пара.
- Количества — конечные JSON-числа, не строки и не NaN. Backend считает количества и округление десятичной арифметикой. В JSON не передавать числа больше безопасного диапазона JS.
- Даты: `YYYY-MM-DD`; временные отметки ответа — ISO 8601 со смещением. Для набора явно задаётся `timezone`.
- `as_of` означает состояние **на начало указанного дня**. История обучения заканчивается до этой даты. Конец интервалов `start_date/end_date_exclusive` не включается. Это исключает двойной учёт последнего дня.
- Горизонт прогноза: `[as_of, as_of + lead_time_days + review_period_days)`. Поставка в последний включённый день учитывается, на дату исключённой границы — нет. Получение происходит в начале дня, потребление — в течение дня.
- `null` означает «неизвестно». Пустое поле/ячейка не становится нулём без явно принятой политики импорта. Неизвестная рекомендация возвращается как `null`, не как 0.
- Исходные Excel-файлы не изменять. Все синтетические примеры помечены `data_kind: synthetic` и не смешиваются с фактическими наборами.

## 2. Нормализованный набор

### Исправление исходных фактов

`POST /datasets/{id}/products/{productId}/corrections` создаёт новый dataset и возвращает его сводку (201). Исходный набор и расчёты не изменяются; у нового расчёта собственный ID и первоначальный статус DRAFT. Ссылки на бинарные оригиналы наследуются.

```json
{
  "author": "Имя менеджера",
  "reason": "Сверено с отчётом склада",
  "stock": {"warehouse_id": "WH1", "as_of": "2026-07-01", "free_stock_qty": 40},
  "purchase": {"purchase_unit": "коробка", "purchase_unit_factor": 12, "category_id": "STANDARD", "moq_purchase_qty": 5, "pack_multiple_purchase_qty": 5},
  "supplier_policy": {"supplier_id": "SUP_A", "lead_time_days": 7, "review_period_days": 7}
}
```

Это синтетический пример, не значения для реального импорта. Объекты `stock`, `purchase`, `supplier_policy` можно опустить/null, но нужен хотя бы один. Переданный `purchase` заменяет все пять своих полей; null в числах сохраняет неизвестность, ноль допустим только для MOQ. Остаток должен быть явно задан неотрицательным числом; склад должен присутствовать в наборе, дата обязательна. Заменяется только снимок данного товара/склада/даты; другие снимки сохраняются. Единица хранения не изменяется. Политика относится только к поставщику выбранного товара, суммарный горизонт 1–366 дней.

В `sources` добавляется ручной источник с полем `correction`: `parent_dataset_id`, `product_id`, `author`, `reason`, `created_at`, `before_product`, `after_product`, `before_stock`, `after_stock`, `supplier_policy`. Для источников без исправления поле отсутствует. Автор — введённое имя, а не подтверждённая учётная запись. История доступна в редакторе товара. Сроки сохраняются в этом источнике и применяются frontend к параметрам нового расчёта; API-клиент должен передать выбранную политику также в `POST /calculations`. Новая категория требует своей политики запаса. Редактор не исправляет транзит, полноту продаж, доступность и карантин и не снимает связанные блокировки.

В PostgreSQL V3 добавляет `datasets.history_dataset_id`: версии с исправлениями ссылаются на владельца неизменяемых рядов (`sales`, `inbound`, coverage, availability, seasonality, monthly и reported). Товары, остатки, источники, замечания и ссылки на файлы сохраняются в транзакции нового набора. Для прямого SQL по историческим таблицам используйте `COALESCE(history_dataset_id, dataset_id)`; API `/data` и `/review` разрешают ссылку автоматически. Последовательные исправления продолжают использовать исходную историю. Параллельные исправления одного родителя создают независимые версии и автоматически не объединяются.

`POST /datasets` принимает объект следующей структуры. Ниже показан каркас, а не готовый запрос: для валидного набора нужен хотя бы один товар и его поставщик. Полный рабочий пример находится в `fixtures/contract/01_baseline.json`, поле `dataset`.

```json
{
  "schema_version": "1.0",
  "name": "Контрольный пример",
  "data_kind": "synthetic",
  "timezone": "Asia/Almaty",
  "suppliers": [],
  "products": [],
  "sales_coverage": [],
  "sales": [],
  "inventory": [],
  "inbound": [],
  "inbound_coverage": [],
  "availability": [],
  "seasonality_profiles": [],
  "sources": [],
  "issues": []
}
```

| Массив | Поля одной записи |
|---|---|
| `suppliers` | `supplier_id`, `name` |
| `products` | `product_id`, `supplier_id`, `sku_1c`, `supplier_article` (nullable), `name`, `stock_unit`, `purchase_unit`, `purchase_unit_factor`, `category_id` (nullable), `moq_purchase_qty` (nullable), `pack_multiple_purchase_qty` (nullable), `source_refs` |
| `sales_coverage` | `product_id`, `warehouse_id`, `start_date`, `end_date_exclusive`, `complete` |
| `sales` | `sale_id`, `product_id`, `warehouse_id`, `date`, `document_id`, `customer_id` (nullable, только обезличенный), `operation_type`, `quantity`, `source_refs` |
| `inventory` | `product_id`, `warehouse_id`, `as_of`, `free_stock_qty` (nullable), `source_refs` |
| `inbound` | `shipment_id`, `product_id`, `warehouse_id`, `quantity`, `expected_date` (nullable), `status: confirmed/unconfirmed`, `source_refs` |
| `inbound_coverage` | `product_id`, `warehouse_id`, `as_of`, `complete` — подтверждает полноту списка открытых поставок на дату |
| `availability` | `product_id`, `warehouse_id`, `start_date`, `end_date_exclusive`, `state: available/stockout/unknown`, `provenance: observed/manual/synthetic`, `source_refs` |
| `seasonality_profiles` | `profile_id`, `scope_type: product/category/supplier`, `scope_id`, `basis: daily_rate`, `indices` (12 чисел, январь–декабрь), `source_refs` |
| `sources` | `source_id`, `kind: xlsx/manual/synthetic`, `role`, `file_name` (nullable), `note`, необязательный `correction` (описан выше) |
| `issues` | `code`, `severity: info/warning/error`, `product_id` (nullable), `message`, `source_refs` |
| `monthly_sales`, `monthly_stock` | Необязательные массивы: `product_id`, `warehouse_id`, `month: YYYY-MM`, `quantity` (nullable, исходный знак сохраняется), `meaning`, `source_refs` |

`source_refs` — массив `{source_id, sheet, cell_range}`; `sheet` и `cell_range` могут быть null для ручного или синтетического источника. Не передавать абсолютные пути компьютера через пользовательский API.

Необязательные массивы исходных данных IEK:

| Массив | Поля одной записи |
|---|---|
| `reported_inbound` | `source_row_id` (уникальный), `product_id`, `reported_quantity` (исходный знак), `unit` (nullable), `arrival_deadline` (nullable), `shipment_label`, `source_refs` |
| `reported_purchase_rules` | `source_row_id` (уникальный), `product_id`, `rule_label`, `raw_value` (nullable, в том числе `#N/A`), `reported_quantity` (nullable), `unit` (nullable), `source_refs` |

Эти массивы сохраняют неподтверждённые исходные факты и **не участвуют в арифметике расчёта**. `arrival_deadline` означает «поступление до», а не день гарантированной доступности. Импорт IEK оставляет нормализованные `inventory`, `inbound`, `inbound_coverage` пустыми: текущего остатка нет, единицы и область транзита неизвестны. Значение «Мин. разр. к отгр.» не назначается автоматически одновременно минимумом и кратностью. Единицы закупки обозначаются «не уточнена», коэффициент пересчёта — null. Дубликаты остаются отдельными строками с замечаниями. Для использования партий аналитик должен подтвердить единицы, коэффициент, склад и дату и внести нормализованные записи с источником в новый dataset; простое подтверждение предупреждения этого не делает.

`monthly_stock.meaning=reported_month_start_stock` для IEK сохраняет начальные месячные остатки, не текущие снимки и не дневную доступность. Пустые ячейки остаются null. В `DatasetSummary.counts` добавлены `reported_inbound` и `reported_purchase_rules`; пустые новые массивы не сериализуются в dataset, поэтому старые нормализованные наборы сохраняют прежний hash.

### Значения и проверки

- `purchase_unit_factor` — число единиц хранения в одной единице закупки, строго больше 0 либо null, если неизвестно. Например, 305 метров на бухту. Не выводить автоматически из названия без подтверждения. Null блокирует расчёт.
- В `sales` `quantity > 0`, а направление задаёт `operation_type: sale/return`. Неопознанные корректировки остаются в карантине импорта. Исходный знак хранится в журнале источника; он не меняется через `abs`.
- При наличии возвратов спрос не рассчитывать молча по модулю или сумме всех движений. Требуется выбранная политика возвратов; пока её нет, затронутые позиции получают `RETURN_POLICY_REQUIRED`. Возвраты не отменяют уже переданный снимок остатка.
- В `inventory` один снимок на товар, склад и дату. Адаптер вычисляет свободный остаток один раз из согласованного источника. Если источник уже содержит свободный остаток, резерв повторно не вычитать.
- В `inbound` количество выражено в единицах хранения. При неопределённой дате нельзя автоматически считать поставку своевременной. Отсутствие записей означает нулевой транзит только при подтверждённой полноте источника в отчёте импорта.
- Периоды наличия одного товара/склада не пересекаются. Stockout и продажа в один день — конфликт данных для упрощённой дневной модели.
- Полное покрытие продаж позволяет трактовать отсутствие события в конкретный день как нулевые продажи. Оно **не доказывает наличие товара** в этот день.
- Сезонные индексы — строго положительные относительные уровни дневного спроса, среднее по 12 месяцам равно 1. Профиль месячных объёмов адаптер сначала переводит в профиль дневной скорости с учётом длины месяца и документирует преобразование.
- Дубликаты ID, конфликтующие снимки и нарушенные внешние ключи — ошибки. Разные строки одной накладной допустимы и агрегируются по документу/товару/складу, а не удаляются как дубликаты.

## 3. Настройки расчёта

Для интерфейса `GET /datasets/{id}/review` возвращает `schema_version`, `name`, `data_kind`, `timezone`, `suppliers`, `products`, `inventory`, `sales_coverage`, `sources`, `issues`, `reported_inbound`, `reported_purchase_rules`. История `sales`, месячные ряды, availability и сезонные профили остаются на backend. Это представление для просмотра, не полный нормализованный набор для повторного `POST /datasets`; полный набор получают через `/data`.

`POST /calculations`:

```json
{
  "dataset_id": "ds_example",
  "as_of": "2026-07-01",
  "warehouse_id": "WH_TEST",
  "supplier_ids": ["SUP_A"],
  "category_ids": [],
  "history_start": "2026-06-01",
  "supplier_policies": [
    {"supplier_id": "SUP_A", "lead_time_days": 7, "review_period_days": 7}
  ],
  "category_policies": [
    {"category_id": "STANDARD", "safety_days": 7, "purchasing_allowed": true}
  ],
  "forecast": {
    "seasonality_mode": "provided",
    "growth_mode": "manual",
    "manual_growth_pct": 0,
    "outlier_policy": "robust_orders_v1",
    "stockout_mode": "confirmed_only"
  },
  "assumptions": []
}
```

- Пустые `supplier_ids/category_ids` означают все значения. Пропущенные/null массивы нормализуются в пустые; предпочтительно передавать явно. Неизвестные значения фильтра возвращают 422.
- `lead_time_days >= 0`, `review_period_days >= 1`, их сумма — от 1 до 366; `safety_days` — от 0 до 366, целые. История начинается раньше `as_of` и ограничена интервалом строго меньше 10 лет.
- `growth_mode: manual/historical`. `manual_growth_pct` от -100 до 10000 включительно, обязателен только для manual; при historical должен быть null. В v1 исключаем одновременное ручное и автоматическое применение одного тренда.
- `seasonality_mode: provided/estimate`. При provided выбирается один профиль: product → category → supplier. При estimate метод и область обучения сохраняются в результатах; недостаточная история даёт `INSUFFICIENT_SEASONAL_HISTORY`, автоматического перехода к предоставленному профилю нет. Не применять два профиля последовательно.
- `robust_orders_v1` означает анализ документа и, если доступен, клиентского агрегата с учётом сезонности и повторяемости. Конкретные параметры детектора сохраняются в `methodology`, версия меняется при изменении поведения. Тесты ниже ограничивают ожидаемое поведение, не подменяют реализацию.
- Неизвестная категория не получает произвольную политику; требуется исправить `category_id` и передать соответствующую политику категории. Допущения `UNCATEGORIZED` в API нет.
- Неизвестные наличие/транзит/остаток не скрывать. Для неполных данных допустим расчёт только по явному допущению с `code`, `scope_id`, `value`, `reason`, `accepted_by`. Факт и допущение сохраняются отдельно.
- Для товаров с недостаточной историей оценки тренда или всплесков возвращать предупреждение либо блокировку, а не выдуманную точность.

### Арифметика и единицы

Для плоского очищенного ряда с известным наличием базовая дневная скорость = продажи в дни наличия / число дней наличия. При сезонности перед усреднением снимается её влияние. Предполагаемый спрос в дни подтверждённого отсутствия выводится отдельно; нули этих дней не должны второй раз уменьшать базовую скорость.

`D_H` — сумма дневного прогноза за горизонт H. Для однозначной приёмки v1 `S` — сумма прогноза за следующие `safety_days` **после конца H**. `Q_raw_stock = max(0, D_H + S - free_stock - eligible_inbound)`.

Переводим потребность в единицы закупки: `Q_raw_purchase = Q_raw_stock / purchase_unit_factor`. При нулевой потребности заказ 0. Иначе:

`Q_purchase = ceil(max(Q_raw_purchase, MOQ_purchase) / pack_multiple_purchase) × pack_multiple_purchase`.

`Q_stock = Q_purchase × purchase_unit_factor`. Если MOQ/кратность/единицы неизвестны, возвращаем статус `NEEDS_INPUT`, количества null и пустые факторы расчёта; согласованное отсутствие ограничения записывается явно как MOQ=0, кратность согласно допустимой единице закупки.

Прогноз дефицита строится отдельно по датам с учётом **имеющихся** поставок, без включения нового рекомендуемого заказа. Утверждение само по себе не создаёт запись inbound. Просроченные неполученные поставки не считать уже доступными.

## 4. Endpoints

| Метод и путь | Запрос | Успех |
|---|---|---|
| `GET /health` | — | 200 `{status: "ok", api_version: "1.0", storage: "postgres"}` (или `file`); 503 при недоступной БД |
| `GET /datasets` | — | 200, массив `DatasetSummary` сохранённых наборов, новые первыми |
| `POST /datasets` | Нормализованный JSON | 201, `DatasetSummary`; 200 при повторном содержимом |
| `POST /datasets/import` | Multipart: `manifest` JSON + файлы по именованным частям | 201, `DatasetSummary`; 200 при повторном содержимом; синхронный импорт |
| `POST /datasets/{id}/products/{productId}/corrections` | `author`, `reason`, хотя бы один из `stock`, `purchase`, `supplier_policy` | 201, сводка нового набора с историей исправления |
| `GET /datasets/{id}` | — | 200, `DatasetSummary` |
| `GET /datasets/{id}/data` | — | 200, полный нормализованный набор, включая все issues и месячные значения |
| `GET /datasets/{id}/review` | — | 200, справочники и отчёт качества без полной истории продаж и месячных рядов |
| `GET /datasets/{id}/files` | — | 200, список `{part_name,file_name,object_key,sha256,byte_size}` оригиналов |
| `GET /datasets/{id}/files/{sha256}` | — | 200, оригинальный файл как attachment; 404, если файл не принадлежит набору |
| `POST /calculations` | Настройки выше | 201, `CalculationResult`, состояние DRAFT |
| `GET /calculations/{id}` | — | 200, актуальный результат |
| `GET /calculations/{id}/items/{item_id}` | — | 200, строка + история/прогноз/аномалии |
| `PATCH /calculations/{id}/items/{item_id}` | `expected_revision`, `final_purchase_qty` (null = сброс), `reason` | 200, обновлённый результат |
| `POST /calculations/{id}/approve` | `expected_revision`, `approved_by`, `acknowledged_issue_codes` | 200, утверждённая версия |

Новый расчёт создаёт новый ID и всегда DRAFT; старое утверждение относится только к старому снимку. Пересчёт не изменяет старый результат. Изменение количества существующего расчёта увеличивает `revision` и сбрасывает его утверждение. Два одновременных изменения проверяют `expected_revision`.

XLSX-экспорт можно добавить после CSV. Endpoint отправки заказа поставщику в v1 отсутствует. `approved_by` — введённое имя для локальной истории MVP, не доказанная аутентификация и не электронная подпись.

### Импорт файлов

Manifest содержит `name`, `data_kind: real`, `timezone`, `files: [{part_name, supplier_id, role}]`. Адаптер выбирается по `supplier_id: SYSTEME` или `IEK`; в одном импорте допустим только один поставщик и ровно по одному файлу каждой из шести ролей: `sales_transactions`, `sales_monthly`, `stock_monthly`, `inventory_transit`, `moq`, `seasonality`. Копии месячной истории и ошибочные сводные формулы из транзитной таблицы не прибавляются к продажам. Пример клиента — `tools/import_supplier.py --supplier IEK` (первый позиционный аргумент — путь ZIP). Старый `tools/import_systeme.py` сохранён как совместимый вход.

API принимает XLSX: 15 МБ на файл, 40 МБ на multipart-запрос; превышение даёт 413. Интерфейс ограничивает сумму файлов 39 МБ, оставляя место для multipart; Python-клиент — 35 МБ. Nginx ограничивает любое тело запроса 40 МБ, включая JSON; разрешённые интерфейсом 150 МБ JSON не гарантируют загрузку через Docker-прокси. Клиентский Python-скрипт читает ZIP в памяти, проверяет шесть файлов, 15 МБ на файл и 35 МБ суммарно. Серверный ZIP-импорт отсутствует. Импорт синхронный; отдельного таймаута обработки сервер пока не задаёт. Повторный импорт того же нормализованного содержимого, имени и параметров возвращает прежний dataset (200, `reused: true`), новый — 201. Это также относится к POST /datasets. ID — SHA-256 нормализованного JSON.

`DatasetSummary`: `dataset_id`, `name`, `data_kind`, `schema_version`, `status: READY/PARTIAL`, `counts`, `sources`, `coverage`, `issues`, `created_at`. `coverage` отдельно отражает даты и область продаж, снимков, наличия, клиентов и транзита. `PARTIAL` не маскирует строки без количества; они отражаются в отчёте карантина.

Дополнительно: `issue_count`, `issues_truncated`, первые 200 issues; поле `reused` возвращается после POST. Статус набора — предварительная оценка, готовность каждой строки для конкретных дат определяется расчётом.

### Поддерживаемые допущения и ограничения адаптера

Каждое допущение: `{code, scope_id, value: true, reason, accepted_by}`. Область — product_id, supplier_id или `*`. Поддержаны:

- `ASSUME_AVAILABLE`: неизвестное дневное наличие считается наличием для сценария; история маркируется `assumed_available`. Подтверждённый stockout не переопределяется.
- `CONFIRM_SALES_COVERAGE`: признаёт полноту существующего интервала покрытия. Не добавляет отсутствующий интервал и не расширяет его даты.
- `CONFIRM_INBOUND_SCOPE`: подтверждает существующий источник транзита на точную дату. Не исправляет неизвестную дату или количество поставки.
- `CONFIRM_SNAPSHOT_SCOPE`: снимает соответствующий вопрос к области исходного снимка. Не меняет дату/количество и не создаёт отсутствующий остаток.
- `EXCLUDE_QUARANTINED_OPERATIONS`: явное согласие исключить операции из карантина. Они не преобразуются в положительные продажи.

Для полей, которые нельзя исправить допущением, нужен новый нормализованный dataset с подтверждёнными значениями и ручными source_refs. Редактор через POST /datasets/{id}/products/{productId}/corrections поддерживает остаток, закупочные единицы/MOQ/кратность, категорию и сроки поставщика; прочие поля исправляют через новый нормализованный JSON. В Systeme `purchase_unit` предварительно повторяет единицу хранения, но коэффициент и MOQ остаются null до подтверждения. В IEK единица закупки обозначена «не уточнена». Месячные остатки IEK обозначены как начальные, момент измерения Systeme не подтверждён; ни из тех, ни из других даты stockout не восстанавливаются. Для сезонного профиля используются L11:L22 с нормализацией по длине месяцев 2025; допущение об интерпретации отмечается предупреждением.

Исторический тренд — линейная регрессия очищенной дневной скорости по полным месяцам: минимум три месяца, в каждом не менее `max(7, floor(число_дней_месяца / 2))` дней наличия (включая явно принятые `assumed_available`, исключая `stockout`). Сезонная оценка требует минимум два полных наблюдения каждого месяца года, не менее 14 дней наличия в каждом; нулевой/недостаточный профиль блокируется. Параметры детектора: минимум 8 документов, порог больше max(3 × медиана, медиана + 3.5 × MAD / 0.67448975), повторяемость сравнимых покупок одного клиента в ≥3 неделях сохраняет событие. Без ID клиента повторяемость оценивается по документам товара, клиентская принадлежность не восстанавливается; ограничение отмечается предупреждением. Это эвристика, требующая оценки на реальных данных.

## 5. Ответ расчёта

Сокращённый пример: массивы истории, прогноза и аномалий, часть факторов и параметры методологии опущены для читаемости.

```json

  "calculation_id": "calc_example",
  "dataset_id": "ds_example",
  "revision": 1,
  "status": "DRAFT",
  "data_kind": "synthetic",
  "as_of": "2026-07-01",
  "warehouse_id": "WH_TEST",
  "methodology": {"version": "replenishment_v1", "parameters": {}},
  "summary": {"supplier_count": 1, "item_count": 1, "needs_input_count": 0},
  "supplier_groups": [{"supplier_id": "SUP_A", "item_ids": ["item_P1"]}],
  "items": [{
    "item_id": "item_P1",
    "product_id": "P1",
    "supplier_id": "SUP_A",
    "sku_1c": "000001_",
    "name": "Контрольный товар",
    "stock_unit": "pcs",
    "purchase_unit": "pcs",

    "warnings": [],
    "assumptions": [],
    "source_refs": []
  }],

```

Пример дефицита предполагает поступление 20 единиц на 8 июля, как в базовом fixture. С 1 по 4 июля остаток 40 покрывает четыре дня по 10, 5 июля возникает неудовлетворённый спрос. Нулевой остаток на конец 4 июля сам по себе ещё не означает потерянную продажу 4 июля.

`item.status`: `READY`, `ASSUMED`, `NEEDS_INPUT`, `EXCLUDED_BY_POLICY`. При блокирующей нехватке данных числовые поля, которые нельзя вычислить, — null. Для запрета закупки по подтверждённой категории количество 0, но неудовлетворённую потребность показываем отдельно.

`urgency`: `BEFORE_NEXT_DELIVERY`, `WITHIN_HORIZON`, `NORMAL`, `UNKNOWN`. Точное правило: дата сравнения — минимум ближайшей существующей поставки и `as_of + lead_time_days` (при отсутствии транзита используется только второе). Если первый неудовлетворённый спрос раньше этой даты, статус BEFORE_NEXT_DELIVERY; если дефицит есть позже или в эту дату внутри H — WITHIN_HORIZON; без дефицита в H — NORMAL; при блокировке — UNKNOWN.

Карточка дополнительно содержит `history: [{date, actual_sales_qty, regular_sales_qty, estimated_lost_qty, availability_state}]`, `forecast: [{date, demand_qty, projected_stock_qty, unmet_demand_qty}]`, `anomalies: [{document_ids, customer_id, date, original_qty, excluded_qty, reason, decision}]`. Эти массивы строятся по дневной истории. Месячные исходные значения остаются в dataset и напрямую не используются ядром; они не выдаются за реальные дневные наблюдения.

Сумму единиц по метрам и штукам не выводить как общий KPI. Стоимость заказа не показывать без сопоставимых закупочных цен и валюты.

## 6. Ошибки, утверждение и экспорт

Ошибка приложения: `{error: {code, message, fields: [], request_id}}`. Сейчас `fields` всегда пустой; детальные ошибки по полям не формируются. Отказ Nginx (например, превышение 40 МБ) может иметь собственный формат ответа. Структурно некорректный JSON/manifest — 400; неизвестный ID — 404; конфликт revision или неутверждённый экспорт — 409; некорректные значения/блокирующая попытка утверждения — 422; превышение объявленного лимита — 413. Не возвращать трассировки и секреты.

Валидный расчёт с неполными данными возвращает 201/200 и `NEEDS_INPUT` по затронутым строкам. Такой результат не утверждается, пока пользователь не предоставит данные. Политика запрета закупки даёт 0 только после успешной проверки входов и не обходит блокировки. Для отдельного набора поставщиков/категорий создаётся новый расчёт с фильтрами. При утверждении `acknowledged_issue_codes` должен включать все коды предупреждений и допущений результата, включая ограничения импорта.

Ручное количество неотрицательно, соответствует единице/кратности и минимуму, если положительно. Ноль допустим как осознанный отказ от заказа с причиной. Нельзя изменить `recommended_*` через PATCH: они сохраняют результат алгоритма. `override` хранит новое значение и причину; null сбрасывает к рекомендации.

CSV: UTF-8 с BOM, разделитель `;`, точка в десятичных числах, строки CRLF, текст экранируется по правилам CSV. Колонки: `supplier_id;sku_1c;supplier_article;name;warehouse_id;as_of;purchase_unit;recommended_purchase_qty;final_purchase_qty;reason`. Текст, начинающийся с формульных символов Excel, экранировать как текст. Коды должны оставаться строками при импорте в учётную систему. Сохранение типов в обычном CSV ограничено; для гарантированного открытия в Excel с ведущими нулями потребуется XLSX либо явная настройка импорта. Формат 1С ещё не подтверждён постановщиком.

Экспорт содержит только положительные окончательные количества выбранного поставщика и соответствует указанным `revision` и утверждению. Имя файла включает ID расчёта, поставщика и revision. Сетевых вызовов поставщику не выполняется.

## 8. PostgreSQL и файлы

По умолчанию профиль `postgres`, миграции Flyway. Каждая строка продаж, месячного ряда и прочих источников хранится отдельной записью с порядковым номером; полный архив не упакован в одну JSONB-строку. Структурированные ключи, количества и даты доступны отдельными SQL-колонками, автоматически вычисленными из JSONB записи. `datasets.summary` — неизменяемая сводка, `/review` не загружает продажи из БД.

Импорт набора и привязка оригинальных файлов записываются одной транзакцией. Бинарные объекты сначала сохраняются через FileStorage по hash; при неудачном импорте может остаться непривязанный объект, но частичного набора в БД не будет. Повторный импорт добавляет только отсутствующие ссылки на оригиналы. Исходные XLSX можно скачать через endpoints выше; ZIP и нормализованный входной JSON отдельно как бинарный оригинал пока не архивируются.

Правка и утверждение блокируют строку расчёта (`FOR UPDATE`), затем проверяют `expected_revision` и сохраняют изменения с событием аудита. Чтение расчёта согласовано с его позициями (`FOR SHARE`). Изменение или ошибка откатывают всю транзакцию; кэш расчётов между процессами не используется. Профиль `file` остаётся явным вариантом для одного процесса без БД; его контракт API совпадает, но распределённых блокировок нет.

Локальный перенос `UITECH_MIGRATE_LOCAL=true` сохраняет идентификаторы и актуальные версии, фиксирует SHA-256 исходного JSON и hash текущей сериализации, не удаляет исходные JSON и не перезаписывает существующие записи PostgreSQL. Старые утверждённые состояния сохраняются, отсутствующая в старых JSON история отдельных правок не выдумывается.
