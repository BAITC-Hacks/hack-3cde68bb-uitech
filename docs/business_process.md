# HACKALEM AI --- Автоматизация формирования заказов поставщикам

## 1. Назначение решения

Сервис автоматизирует расчёт потребности в пополнении склада и формирует
рекомендации менеджеру отдела закупа.

**Основной пользователь:** менеджер отдела закупа.

Ключевой принцип: система автоматизирует подготовку закупочного решения,
но финальное решение остаётся за ответственным сотрудником. Заказ не
отправляется поставщику без подтверждения сотрудника.

## 2. Бизнес-проблема

Текущий процесс основан на ручной консолидации данных в Excel. Это
приводит к избыточным запасам, дефициту, упущенным продажам и высокой
трудоёмкости анализа.

Система должна учитывать историю продаж, текущие остатки, товары в пути,
категории, прогноз прироста, периоды отсутствия товара, поставщиков и
сроки поставки.

## 6. Алгоритм №1 --- базовая потребность

Цель --- определить количество заказа по каждому SKU.

``` text
Target Stock = Forecast Demand + Safety Stock

Recommended Order =
max(0, Target Stock - Current Stock - In Transit)
```

Пример:

``` text
Forecast Demand = 600
Safety Stock    = 100
Current Stock   = 200
In Transit      = 150

Target Stock = 700
Recommended Order = 350
```

Изменение любого существенного входного параметра должно отражаться на
результате.

> Точная политика Safety Stock и конкретное влияние категории товара
> исходным ТЗ не определены. Это проектное решение команды либо вопрос
> для уточнения у партнёра.

## 7. Алгоритм №2 --- сезонность и устойчивый рост

Прогноз должен учитывать структуру временного ряда:

``` text
Sales History
     |
     +-- Level
     +-- Trend
     +-- Seasonality
             |
             v
       Demand Forecast
```

Пример сезонности:

``` text
Jan 100
Feb 100
Mar 110
Apr 130
May 250
Jun 550  <- сезонный пик
Jul 250
```

Прогноз июня должен отражать сезонный пик, а не среднее по всей истории.

Устойчивый рост:

``` text
2023 -> 300
2024 -> 350
2025 -> 410
2026 -> 480
```

Такое повышение учитывается как тренд, а не как единичный выброс.

Для MVP при достаточной истории можно использовать Holt-Winters /
Exponential Smoothing либо другой объяснимый алгоритм временных рядов.

## 8. Алгоритм №3 --- компенсация stockout

Если товара нет, фактическая продажа 0 не означает спрос 0.

``` text
RAW SALES:
12 11 10 0 0 0 12
         [stockout]

CORRECTED DEMAND:
12 11 10 11 11 11 12
```

Алгоритм:

1.  Найти периоды отсутствия товара.
2.  Не считать нули в эти периоды нормальным нулевым спросом.
3.  Оценить потенциальный спрос по доступной истории.
4.  Сформировать corrected demand.
5.  Передать скорректированный ряд в прогноз.

Оценка может учитывать соседние периоды, историю SKU, день недели,
сезонность, тренд и при необходимости категорию.

## 9. Алгоритм №4 --- разовые крупные заказы

Цель --- не позволить единичной крупной продаже существенно завысить
регулярный прогноз.

``` text
10 -> 11 -> 12 -> 500 -> 10 -> 11
                  ^
          one-time bulk order
```

Сигналы:

-   IQR, MAD / robust Z-score, rolling median;
-   высокая концентрация продажи на одном обезличенном клиенте;
-   возврат спроса к обычному уровню после всплеска.

Важно отличать разовый заказ от тренда:

``` text
Разовый: 10 11 12 500 10 11
Тренд:   10 12 15 20 30 40 50
```

Исходная транзакция сохраняется:

``` text
actual_sales   = 500
regular_demand = 11
```

Для регулярного прогноза выброс исключается либо заменяется устойчивой
оценкой нормального спроса.

## 11. Риск дефицита и срочность

Опциональная функция --- приоритизация по риску дефицита.

``` text
Days of Stock = Current Stock / Expected Daily Demand
```

Если:

``` text
Days of Stock < Lead Time
```

риск stockout повышается.

Пример:

``` text
Current Stock = 60
Daily Demand  = 20
Days of Stock = 3 дня
Lead Time     = 14 дней

Risk = HIGH
```

Конкретные пороги High / Medium / Low должны быть зафиксированы
командой.

## 12. Условия поставщика

Опционально учитываются минимальная партия и условия поставщика.

``` text
Calculated Order = 347
MOQ / pack size  = 100
Final Order      = 400
```

Такая корректировка должна отображаться в объяснении.

## 13. Explanation Engine

Каждая рекомендация должна отвечать на вопрос: **почему предложено
именно такое количество?**

Пример trace:

``` json
{
  "sku": "ABC-123",
  "recommended_qty": 350,
  "forecast_demand": 600,
  "safety_stock": 100,
  "current_stock": 200,
  "in_transit": 150,
  "seasonality_effect": 0.20,
  "trend_effect": 0.08,
  "estimated_lost_demand": 35,
  "excluded_bulk_sales": 500,
  "urgency": "high"
}
```

Пример объяснения:

> Рекомендуется заказать 350 шт. Прогнозируемая потребность --- 600 шт.,
> страховой запас --- 100 шт. В наличии 200 шт., ещё 150 шт. находятся в
> пути. Учтены сезонность, устойчивый рост и оценочный спрос периода
> отсутствия товара; разовый крупный заказ исключён из регулярного
> спроса.

Для MVP объяснение желательно формировать детерминированным шаблоном из
реального trace расчёта.

## 16. Выход системы

Минимальный результат:

-   артикул;
-   поставщик;
-   рекомендуемое количество;
-   обоснование;
-   срочность;
-   группировка по поставщику.

Формат: таблица / dashboard с экспортом и совместимостью с текущей
учётной системой.

## 17. Опциональные возможности

-   приоритизация по риску дефицита;
-   минимальная партия и условия поставщика;
-   визуализация трендов спроса по категориям;
-   автоматическая выгрузка/рассылка сформированного заказа после
    подтверждения сотрудником.

## 18. Ограничения

1.  Нельзя автоматически отправлять заказ без подтверждения.
2.  Нельзя использовать неанонимизированные данные клиентов.
3.  Расчёт должен быть объяснимым.
4.  Алгоритм должен быть устойчив к аномалиям и выбросам.
5.  Выход должен быть совместим с текущей учётной системой.
6.  Для разработки и тестирования допустимы реалистичные синтетические
    данные.

## 21. Проверки Must Have

### Test 1 --- влияние входных данных

Изменение остатка, товара в пути, прогноза прироста и других
предусмотренных входов должно отражаться на результате.

### Test 2 --- сезонность

SKU с повторяющимся сезонным пиком должен получить прогноз, отражающий
этот пик, а не простое среднее.

### Test 3 --- stockout

Для SKU с отсутствием товара расчёт на corrected demand должен учитывать
положительный оценённый упущенный спрос и давать более высокую
потребность, чем расчёт по сырым продажам.

### Test 4 --- крупный разовый заказ

Искусственно добавленный крупный заказ одному клиенту не должен
существенно увеличивать регулярную рекомендацию.

### Test 5 --- итоговый список

Каждая рекомендуемая позиция должна иметь поставщика, количество,
объяснение и быть доступна в разбивке по поставщику.
