# SupplyMind — бизнес-процесс формирования заказов поставщикам

Документ описывает текущий MVP и отдельно сохраняет предложения по развитию. Методология: [algorithms.md](algorithms.md), поля API: [api-contract.md](api-contract.md), ограничения источников: [DATA_AUDIT.md](DATA_AUDIT.md).

## Цель

SupplyMind помогает менеджеру закупа определить, что, сколько и у какого поставщика заказать. Менеджер проверяет рекомендации, корректирует количество и утверждает результат. Финальное решение остаётся за сотрудником.

## Фактические источники

Реализованы адаптеры шести типов XLSX для IEK и Systeme Electric. Поставщика выбирает пользователь; роли файлов распознаются для известных шаблонов. Универсального определения произвольной схемы Excel и прямого подключения к 1С нет. Также поддерживается нормализованный JSON.

| Источник | Использование в текущем MVP |
|---|---|
| Транзакционные продажи | История спроса, исключение разовых всплесков, оценка тренда и сезонности |
| Месячные продажи | Сохранение и сверка с детализацией; непосредственно в прогноз не добавляются |
| Месячные остатки | Сохранение для анализа; не заменяют актуальный остаток и календарь наличия |
| Текущий остаток | Используется для выбранных даты и склада; неизвестный остаток блокирует расчёт |
| Товары в пути | Нормализованные подтверждённые поставки с датами и складом; требуется подтверждение полноты источника |
| Сезонность | Предоставленный профиль либо оценка по истории SKU при достаточных данных |
| MOQ и кратность | Раздельные ограничения в единицах закупки после пересчёта из единиц хранения |

В IEK актуальный остаток отсутствует. Исходные партии и ограничения отгрузки сохраняются как `reported_inbound` и `reported_purchase_rules`. Они не становятся расчётным транзитом и правилами закупки без подтверждения смысла полей, единиц и области данных. Отсутствие нормализованных поставок не означает нулевой транзит.

## Нормализация поставщиков

Коды 1С хранятся строками с сохранением ведущих нулей. В адаптерах внутренний `product_id` состоит из поставщика и кода, например `IEK:<код>`; `sku_1c` хранится отдельно. Поля разных файлов одного поставщика связываются через этот код. Это не глобальный каталог взаимозаменяемых товаров разных поставщиков.

Адаптеры приводят колонки, даты, количества и реквизиты к общей модели. Расчётное ядро работает с нормализованными сущностями и не читает конкретный Excel-шаблон.

## Реализованный процесс

```text
XLSX IEK / Systeme Electric или нормализованный JSON
  -> выбор поставщика и сопоставление ролей файлов
  -> нормализация и проверка качества
  -> уточнение недостающих данных и параметров
  -> исключение разовых крупных заказов из регулярного спроса
  -> оценка спроса с учётом заданных периодов отсутствия товара
  -> прогноз: уровень спроса, сезонность, рост
  -> потребность: спрос + страховой запас - остаток - допустимый транзит
  -> перевод единиц, MOQ и кратность
  -> прогноз наличия по дням и риск дефицита
  -> объяснение и группировка по поставщику
  -> проверка и корректировка количества с причиной
  -> утверждение версии расчёта
  -> CSV по выбранному поставщику
```

## Работа менеджера

1. Загружает файлы и проверяет отчёт качества. При необходимости уточняет остаток, категорию, единицы закупки, MOQ, кратность и сроки поставщика через редактор исходных данных.
2. Выбирает дату, склад, поставщика и/или категорию, период истории и параметры расчёта. Правка источников создаёт новый набор с автором, причиной и историей до/после; старые расчёты сохраняются.
3. Запускает расчёт. Нехватка обязательных сведений даёт `NEEDS_INPUT`; неизвестные значения не подменяются нулями. Поддерживаемые явные допущения сохраняются в результате.
4. Проверяет остаток, учтённый транзит, риск дефицита и количество. В карточке видит прогноз, страховой запас, потребность до округления, правила закупки, исключённые операции и объяснение.
5. При необходимости меняет количество с причиной. Готовую позицию можно исключить из CSV, установив количество `0`. Отдельных статусов «принята/отклонена» пока нет; заблокированную позицию таким способом исключить нельзя.
6. Утверждает весь расчёт конкретной версии, подтверждая предупреждения и допущения. Хотя бы одна позиция `NEEDS_INPUT` блокирует утверждение. Изменение количества снимает прежнее утверждение.
7. Скачивает CSV по выбранному поставщику. Экспорт доступен только для актуальной утверждённой версии и включает позиции с положительным итоговым количеством.

Совместимость CSV с конкретной конфигурацией учётной системы компании пока не подтверждена. Её нужно согласовать и проверить для выполнения соответствующего ограничения ТЗ. Экспорт не является прямой интеграцией с 1С.

## Отсутствие товара и упущенный спрос

**Реализовано:** компенсация по заданному календарю наличия, режим `confirmed_only`. Продажи в дни наличия определяют базовую скорость спроса, по которой оценивается упущенный спрос за дни `stockout`. Неизвестное наличие требует данных либо явного допущения `ASSUME_AVAILABLE`; это допущение не восстанавливает периоды отсутствия и не создаёт компенсацию за них.

**Предложение по развитию:** оценивать вероятное отсутствие по низкому/нулевому месячному остатку, падению продаж и спросу до/после периода. Этот метод пока не реализован. Его результат нужно обозначать как `Estimated Stockout / Estimated Lost Demand`, показывать неопределённость и не выдавать оценочные дни за наблюдаемые. Месячная гранулярность не позволяет достоверно установить точное число дней отсутствия.

ТЗ проверяет компенсацию для артикула с зафиксированным stockout. Этот сценарий проверяется на контрольном наборе; автоматическая оценка отсутствия из месячных остатков — дополнительный способ работы с неполными реальными данными.

## Товары в пути

Даты поступления участвуют в прогнозе наличия. Поздняя поставка не скрывает ранний дефицит. Для количества заказа учитываются подтверждённые поступления внутри горизонта «срок поставки + период между заказами»; поступление на исключённой правой границе горизонта не вычитается.

## MOQ и кратность

MOQ означает минимальную партию, кратность — шаг округления. При потребности 347 единиц, коэффициенте перевода 1, MOQ 100 и кратности 100 получается заказ 400. При том же MOQ и кратности 1 получится 347. Нулевая потребность не создаёт заказ из-за MOQ. Менеджер видит исходную потребность и ограничения закупки в карточке товара.

## Отображение результата

Основная таблица показывает товар/код/поставщика, статус, свободный остаток, учтённый транзит, риск дефицита и количество к заказу. Карточка содержит прогноз, страховой запас, исходную потребность, MOQ, кратность, единицы, историю и объяснение. Ближайшая дата поступления отдельным полем рекомендации пока не выводится.

**Предложения по развитию:** добавить ближайшую ожидаемую поставку и явные действия «принять/отклонить» для каждой позиции, сохранив проверки полноты данных, причины изменений и утверждение версии.

## Ограничения и дальнейшая проверка

- В реальных выгрузках нет ID клиента. Проверяются накладные; принадлежность нескольких накладных одному клиенту без идентификатора не доказывается. Клиентский сценарий проверяется на синтетических данных.
- Параметры страхового запаса, сроков поставки, применимость сезонных профилей и ограничения закупки требуют согласования с партнёром. Текущая политика описана в [algorithms.md](algorithms.md).
- Исторический backtest, сравнение моделей и измерение точности на данных компании пока не выполнены.
- Отправка заказов поставщикам не реализована. Решение не отправляет заказ автоматически; финальное решение принимает сотрудник.
- Уточнения, не поддержанные редактором, вносятся через нормализованный JSON с последующим пересчётом.

## Ожидаемая бизнес-ценность

Более частый пересчёт, сокращение ручной консолидации Excel, прозрачность закупочных решений, снижение избыточных запасов и риска дефицита — ожидаемые эффекты. Экономия, сокращение упущенных продаж и повышение точности на данных компании пока не измерены.
