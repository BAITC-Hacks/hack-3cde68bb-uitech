# SupplyMind — анализ и план решения

Задача: автоматический расчёт заказов поставщикам для пополнения склада. Постановщик: «Электрокомплект». Команда: uitech. Реализованы расчётное ядро, backend API, импорт Systeme Electric и IEK, frontend, PostgreSQL и редактор исходных данных. Документ сохраняет анализ требований и первоначальный план этапов; подробная текущая методология — в [algorithms.md](algorithms.md), процесс — в [business_process.md](business_process.md), запуск и результаты проверок — в [README](../README.md). Метрики качества на реальных данных не измерены.

## 1. Рекомендация

Строим рабочее место менеджера закупа: загрузить данные → проверить качество → рассчитать регулярную потребность → увидеть объяснение каждой позиции → скорректировать и утвердить → экспортировать заказ по поставщику.

Основное преимущество MVP — воспроизводимый расчёт и прозрачное влияние сезонности, роста, дефицита и разовых продаж. Первым был подключён Systeme Electric: в его файле «в пути» есть категории и снимок остатков. Затем подключён IEK. Оба адаптера реализованы; отсутствие полей у IEK не скрываем.

## 2. Обязательные требования и приёмка

Источник: раздел 7 PDF. В документе нет числовых весов критериев.

| Требование | Что реализовать | Как доказываем |
|---|---|---|
| Учёт всех источников | Продажи, остаток, поставки в пути, категория, прогноз прироста | На тесте с положительной потребностью поочерёдно меняем входы и проверяем ожидаемое влияние до округления |

| Упущенный спрос при stockout | Отдельная оценка по подтверждённым дням отсутствия | При одинаковых продажах и меньшем числе дней наличия оценка спроса растёт |
| Разовые крупные заказы, в том числе одному клиенту | Фильтр аномальных заказов и клиентских агрегатов с журналом исключений | Вставляем крупную разовую продажу: обычное среднее заметно меняется, очищенный регулярный прогноз остаётся в установленном допуске |
| Группировка и объяснение | Заказы по поставщикам, числовая расшифровка каждой позиции | Для каждой строки видно происхождение количества и применённые ограничения |

Дополнительно из сценария и ограничений: ручная корректировка, утверждение, экспорт, приватность, воспроизводимый README. Без подтверждения сотрудника отправлять заказ поставщику запрещено. В MVP выполняем локальное утверждение и скачивание файла, внешнюю отправку не реализуем.

MOQ и приоритизация в ТЗ опциональны. Они уже поддерживаются частью данных и полезны после пяти обязательных требований.

## 3. Данные и ограничения

Подробный разбор: [DATA_AUDIT.md](DATA_AUDIT.md). Всего 12 XLSX, около 249 тысяч строк детализации с кодами. Файлы доступны локально и не требуют внешнего API для основного расчёта.

Ключевые пробелы: ID клиента, точные периоды stockout, актуальные остатки IEK, сроки новых поставок, правила категорий. Без них нельзя честно заявить полное подтверждение решения на реальных данных.

Два явно разделённых режима:

- **Реальные выгрузки:** читаем все файлы, показываем полноту и расхождения. При недостатке критичного поля выводим «нужны данные» или явно согласованный сценарный расчёт с указанными допущениями.
- **Контрольные примеры:** небольшой синтетический набор с клиентами, ежедневным наличием, категориями и сроками. Он проверяет все must-have и обозначается как синтетический. Его показатели не выдаём за бизнес-эффект на данных компании.

Не считать пропуски нулями автоматически. Номер накладной не является ID клиента. Помесячные остатки не дают точную длительность отсутствия. Детальные и месячные продажи не складываются: сейчас прогноз использует детализацию, месячные продажи сохраняются для сверки. Историческое дополнение месячными данными пока не реализовано и требует подтверждения общей области источников.

## 4. Минимальная архитектура

Один репозиторий организатора, два приложения:

```text
frontend/                  интерфейс менеджера
backend/                   Java: импорт, расчёт, проверка, экспорт
docs/                      методология, схема API, запуск
```

Реализованный стек: Java 17 / Spring Boot с REST API и React / TypeScript / Vite. XLSX читает Apache POI через SAX из временного файла. Версии и зависимости зафиксированы в [README](../README.md) и файлах сборки.

Внутри backend разделяем импорт, нормализацию, оценку спроса, рекомендации и экспорт обычными модулями. Данные импортируем один раз на набор, расчёты выполняем по нормализованным агрегатам. Основное хранилище — PostgreSQL с Flyway; оригиналы XLSX сохраняет локальный FileStorage. Режим `file` с JSON остаётся явно выбираемым вариантом без БД. MinIO/S3 не подключён.

**Отдельный AI-agent не нужен для первой версии.** Вычисления должны быть детерминированными и проверяемыми. Если останется время и понадобится AI-функция, добавим объяснение/сравнение сценариев по уже рассчитанным факторам. Модель не определяет количество заказа и не отправляет его. Ключевой сценарий работает без API-ключа.

## 6. Расчётный алгоритм

Ниже — краткое описание текущей методологии. Точные формулы, пороги и ограничения — в [algorithms.md](algorithms.md). Их качество на реальных данных ещё требуется оценить.

### 6.1. Очистка и выбор области

Выбираем дату расчёта, склад, поставщика/категорию и период обучения. Сохраняем оригинальные строки. Нормализуем даты, коды, числовые значения, типы операций. Отрицательные значения анализируем как возможные возвраты/корректировки; не превращаем их в продажи через модуль.

Не смешиваем остатки всех складов с продажами одного. Для текущей сентябрьской выгрузки тренд сначала оцениваем по полным месяцам до августа 2026 включительно. Неполный сентябрь не участвует в регрессии исторического тренда, но его продажи могут входить в базовую скорость выбранного периода. Дату отчёта показываем в интерфейсе.

### 6.2. Исключение разовых продаж

Агрегируем положительные продажи по товару, складу, дате и накладной; при наличии `customer_id` также проверяем сумму покупок клиента за день. Недели используются для проверки повторяемости, не как отдельный клиентский агрегат.

Сезонно нормализованное количество сравнивается с порогом `max(3 × median, median + 3.5 × MAD / 0.67448975)`. Превышение — кандидат, не доказательство разового спроса. Сопоставимые покупки в трёх и более неделях сохраняются.

При MAD=0 действует порог `3 × median`. При менее чем восьми агрегатах исключение не выполняется; показывается предупреждение. Пороги текущей версии фиксированы в коде и сохраняются в methodology. Медиана всех дней с нулями не используется как единственный прогноз редких продаж.

Сравниваем всплеск с повторяемостью заказов, общей динамикой и сезонным паттерном. Устойчивый рост нескольких периодов не удаляем как единичный выброс. Выявленный правилом разовый заказ исключаем из обучающего ряда регулярного спроса, но сохраняем в фактических продажах и движении запаса. Для дневного всплеска с регулярными и разовыми заказами исключаем конкретные операции, не весь день. Показываем причину исключения. Отдельной ручной отмены решения детектора в интерфейсе пока нет; менеджер может изменить итоговый заказ с причиной.

### 6.3. Компенсация stockout

При подтверждённых днях отсутствия оцениваем нормальную скорость спроса по сопоставимым дням наличия, с сезонной поправкой. Пример: 200 единиц за 20 дней наличия в 30-дневном периоде → 10 в день → оценка 100 упущенных единиц и 300 полного спроса. Это демонстрационная арифметика при постоянном спросе, не измерение фактических потерянных продаж.

При нуле дней наличия возвращаем `NO_AVAILABLE_HISTORY`; профиль поставщика не заменяет отсутствующую базовую скорость. Если календаря наличия нет, не выдаём нулевой остаток на начало месяца за stockout всего месяца. Неизвестное наличие блокирует расчёт либо явно принимается как `ASSUME_AVAILABLE`, без компенсации отсутствия. Заданные периоды можно передать нормализованным JSON с происхождением; автоматической оценки по месячным остаткам нет.

### 6.4. Сезонность и рост

Строим полный временной ряд регулярного спроса в пределах подтверждённого покрытия данных. Очищаем разовые события и оцениваем скорость по дням наличия со снятием сезонности. Упущенный спрос выводим отдельно; повторно прибавлять его к прогнозу нельзя. Пропуски за пределами покрытия не заполняем нулями.

Режим `provided` выбирает предоставленный профиль SKU → категория → поставщик. Режим `estimate` оценивает профиль SKU при достаточной истории, иначе блокирует расчёт. Автоматический переход из estimate к профилю категории/поставщика пока не реализован. Поставленные таблицы сезонности учитываем как внешний профиль/ориентир, но не применяем повторно поверх того же сезонного эффекта. Для расчёта базовой скорости снимаем сезонность, для прогнозного месяца возвращаем её.

Устойчивый рост оцениваем по нескольким завершённым периодам после снятия сезонности. Внешний прогноз прироста делаем отдельным настройочным источником: выбираем либо «исторический тренд», либо «прогноз менеджера»; совместное применение в v1 запрещено. Одно и то же увеличение не учитываем дважды. Для нового/редкого товара показываем ограниченность истории.

В ручном режиме `d(t) = base_daily_rate × season(t) × (1 + manual_growth_pct / 100)`. В историческом режиме `d(t) = max(0, intercept + slope × month_offset(t)) × season(t)`. Это альтернативные режимы; ограничения параметров валидируются.

### 6.5. Рекомендация заказа

```text
H = lead_time_days + review_period_days
D_H = сумма прогнозного спроса по дням горизонта H
S = прогнозный спрос за safety_days после конца H согласно политике категории
A = свободный остаток в выбранной области на дату расчёта
O_H = подтверждённые поставки, прибывающие до конца горизонта H
Q_raw = max(0, D_H + S - A - O_H)
```

При `Q_raw = 0` заказ равен 0. Иначе сначала `Q_purchase_raw = Q_raw / purchase_unit_factor`, затем `Q_purchase = ceil(max(Q_purchase_raw, moq_purchase_qty) / pack_multiple_purchase_qty) × pack_multiple_purchase_qty`. MOQ и кратность — разные поля в единицах закупки. Коэффициент перевода должен быть подтверждён; неизвестные правила не заменяем молча единицей.

Отдельно строим прогноз остатка по датам поступлений. Поставка после ожидаемого дефицита может уменьшать общий заказ, но не устраняет ранний дефицит; показываем его и дату. Не вычитаем весь транзит без учёта дат. Уже свободный остаток повторно не уменьшаем на резерв.

Для объяснения строки показываем: базовый спрос, сезонный/ростовой вклад, компенсацию отсутствия, исключённые события, горизонт, страховой запас, остаток, учтённый транзит и округление.

## 7. Интерфейс MVP

1. **Загрузка и качество данных.** Выбор поставщика, загрузка XLSX/набора, дата отчёта, сопоставленные SKU, пропущенные источники и ошибки. Обязательная настройка отсутствующих параметров.
2. **Рекомендации.** Группировка по поставщику, фильтры по категории/срочности/статусу. В таблице: товар/код/поставщик, статус, остаток, учтённый транзит, риск и итоговое количество. Прогноз, рекомендованное количество и причина правки доступны в карточке.
3. **Карточка SKU.** История и очищенный спрос, отмеченные всплески, прогноз, расчёт количества и допущения. В интерфейсе открывается модальная карточка.
4. **Проверка и экспорт.** Ручные изменения с причиной, утверждение конкретной версии расчёта, скачивание CSV по поставщику; XLSX-экспорт не реализован. Новый расчёт создаётся как DRAFT и не меняет утверждение старого снимка. Правка количества существующего расчёта снимает его утверждение. Формат для 1С уточнить; до этого экспорт называем таблицей заказа, не готовой интеграцией.

Роли/регистрация, чат, отдельный AI-сервис, автоматическая рассылка и прямая интеграция с 1С не реализованы.

## 9. Проверки, которые определяют готовность

- Обычный товар: ручной расчёт совпадает с системой.
- Разовый заказ 100× обычного: записан в журнал исключений; регулярный прогноз меняется не более согласованного допуска. Начальный инженерный ориентир для контролируемого теста — 5%, это не критерий организатора. Проверяем до округления и отдельно после него.
- Один клиент дробит крупный заказ на несколько накладных: клиентский агрегат всё равно выявляет событие.
- Повторяющиеся крупные покупки и устойчивый рост не исключаются автоматически как разовые.
- Сезонный ряд: прогноз воспроизводит следующий сезонный пик.
- Stockout: известные дни отсутствия увеличивают оценку полного спроса; неизвестные периоды не порождают фиктивную компенсацию.
- Больше свободного остатка или своевременного транзита — меньше неокруглённый заказ в тесте без насыщения нулём. Поздний транзит не маскирует ранний дефицит.
- Категория и прогноз прироста реально изменяют расчёт через явно заданные политики.
- Возвраты, нулевая история, MAD=0, новый товар, неизвестная категория, ошибка MOQ, дубликат и пропуск ключевого источника дают определённый результат/статус.
- Экспорт совпадает с утверждённой версией и ручными корректировками; сам ничего не отправляет.
- Контроль повторного импорта исключает двойной учёт данных. Один ввод с одной конфигурацией даёт одинаковый результат.

Для будущей оценки качества прогноза при наличии сопоставимых данных планируется последовательное тестирование на завершённых месяцах: обучаемся только на более ранних данных, сравниваем с простым средним/сезонным прошлогодним прогнозом. Планируем считать MAE/WAPE и систематическое смещение только на наблюдаемых сопоставимых периодах. При нулевой сумме факта WAPE не определён. Настройки, сезонность и тренд для каждого тестового среза не используют будущие данные.

Снижение заказа после исключения всплеска не равно доказанной экономии. Денежный эффект и сокращение дефицита можно заявлять лишь после отдельной проверки с ценами, истинным спросом и сопоставимыми условиями.

## 10. Текущее состояние и следующие шаги

Работают расчётное ядро, API утверждения/экспорта, импорт всех шести файлов Systeme Electric и IEK и frontend React / TypeScript. 17 контрольных сценариев проходят; сквозные сценарии интерфейса проверены в браузере. Реальный импорт даёт PARTIAL: отсутствующие бизнес-правила и подтверждения не подменяются фактами. Следующие этапы — уточнить данные с Altynbek, проверить расчёт на согласованном реальном наборе. IEK подключён; исходные партии и ограничения закупки сохраняются отдельно до подтверждения единиц и смысла полей. Добавлен редактор остатка, правил закупки, категории и сроков поставщика: автор, причина, история до/после, новый неизменяемый набор и переход к пересчёту. Остальные сведения уточняются через нормализованный JSON. История продаж исправленных наборов в PostgreSQL не дублируется. Сводки месяцев сохраняются и используются для отчёта о расхождениях; объединение их с детализацией для прогноза требует подтверждения области источников. Backtest остаётся отдельным этапом. Добавлены PostgreSQL, миграции Flyway, транзакционные правки с аудитом и перенос старых JSON. Оригиналы XLSX сохраняются через локальный FileStorage, метаданные — в БД; S3/MinIO остаётся отдельным последующим этапом.
