# uitech — анализ и план решения

Задача: автоматический расчёт заказов поставщикам для пополнения склада. Постановщик: «Электрокомплект». Документ описывает целевое решение. Реализованы расчётное ядро, backend API, импорт Systeme Electric и frontend для сквозного сценария. IEK ещё предстоит. Метрики качества на реальных данных не измерены. Фактический запуск — в README.

## 1. Рекомендация

Строим рабочее место менеджера закупа: загрузить данные → проверить качество → рассчитать регулярную потребность → увидеть объяснение каждой позиции → скорректировать и утвердить → экспортировать заказ по поставщику.

Основное преимущество MVP — воспроизводимый расчёт и прозрачное влияние сезонности, роста, дефицита и разовых продаж. Для первой сквозной реализации используем Systeme Electric: в его файле «в пути» уже есть категории и снимок остатков. Затем подключаем IEK вторым адаптером. Оба поставщика входят в целевой MVP; отсутствие полей у IEK не скрываем.

## 2. Обязательные требования и приёмка

Источник: раздел 7 PDF. В документе нет числовых весов критериев.

| Требование | Что реализовать | Как доказываем |
|---|---|---|
| Учёт всех источников | Продажи, остаток, поставки в пути, категория, прогноз прироста | На тесте с положительной потребностью поочерёдно меняем входы и проверяем ожидаемое влияние до округления |
| Сезонность и устойчивый рост | Помесячный прогноз с сезонным профилем и трендом | Сезонный тест сохраняет пик; серия растущих периодов повышает прогноз |
| Упущенный спрос при stockout | Отдельная оценка по подтверждённым дням отсутствия | При одинаковых продажах и меньшем числе дней наличия оценка спроса растёт |
| Разовые крупные заказы, в том числе одному клиенту | Фильтр аномальных заказов и клиентских агрегатов с журналом исключений | Вставляем крупную разовую продажу: обычное среднее заметно меняется, очищенный регулярный прогноз остаётся в установленном допуске |
| Группировка и объяснение | Заказы по поставщикам, числовая расшифровка каждой позиции | Для каждой строки видно происхождение количества и применённые ограничения |

Дополнительно из сценария и ограничений: ручная корректировка, утверждение, экспорт, приватность, воспроизводимый README. Без подтверждения сотрудника отправлять заказ поставщику запрещено. В MVP выполняем локальное утверждение и скачивание файла, внешнюю отправку не реализуем.

MOQ и приоритизация в ТЗ опциональны. Они уже поддерживаются частью данных и полезны после пяти обязательных требований.

## 3. Данные и ограничения

Подробный разбор: [DATA_AUDIT.md](DATA_AUDIT.md). Всего 12 XLSX, около 249 тысяч строк детализации с кодами. Файлы доступны локально и не требуют внешнего API для основного расчёта.

Ключевые пробелы: ID клиента, точные периоды stockout, актуальные остатки IEK, сроки новых поставок, правила категорий. Без них нельзя честно заявить полное подтверждение решения на реальных данных.

Два явно разделённых режима:

- **Реальные выгрузки:** читаем все файлы, показываем полноту и расхождения. При недостатке критичного поля выводим «нужны данные» или явно согласованный сценарный расчёт с указанными допущениями.
- **Контрольные примеры:** небольшой синтетический набор с клиентами, ежедневным наличием, категориями и сроками. Он проверяет все must-have и обозначается как синтетический. Его показатели не выдаём за бизнес-эффект на данных компании.

Не считать пропуски нулями автоматически. Номер накладной не является ID клиента. Помесячные остатки не дают точную длительность отсутствия. Детальные и месячные продажи не складываются: выбираем один источник на один период и склад, второй используем для сверки или явно обозначенного исторического дополнения при совпадении области данных.

## 4. Минимальная архитектура

Один репозиторий организатора, два приложения:

```text
frontend/                  интерфейс менеджера
backend/                   Java: импорт, расчёт, проверка, экспорт
docs/                      методология, схема API, запуск
```

Предложение по стеку: знакомый Rajan Java backend с REST API; frontend на знакомом доступном стеке, например React + TypeScript. Точные версии фиксируем при старте реализации. Для чтения XLSX в Java подходит Apache POI; для больших листов предусмотрен событийный API, что позволяет не держать всю книгу как дерево объектов. Источник: https://poi.apache.org/components/spreadsheet/.

Внутри backend разделяем импорт, нормализацию, оценку спроса, рекомендации и экспорт обычными модулями. Данные импортируем один раз на набор, расчёты выполняем по нормализованным агрегатам. Для MVP достаточно локального хранения загруженного набора и JSON-результатов с `dataset_id`/`calculation_id`; отдельную СУБД добавлять только при необходимости.

**Отдельный AI-agent не нужен для первой версии.** Вычисления должны быть детерминированными и проверяемыми. Если останется время и понадобится AI-функция, добавим объяснение/сравнение сценариев по уже рассчитанным факторам. Модель не определяет количество заказа и не отправляет его. Ключевой сценарий работает без API-ключа.

## 5. Контракт данных

Контракт v1 зафиксирован в [api-contract.md](api-contract.md). Контрольные примеры описаны в [ACCEPTANCE_CASES.md](ACCEPTANCE_CASES.md) и сохранены в `fixtures/contract/`. Все 17 проверяются автоматическими тестами backend.

| Сущность | Минимальные поля |
|---|---|
| Товар | supplier_id, sku_1c, supplier_article, name, unit, category_id, MOQ, pack_multiple, purchase_unit_factor |
| Продажа | date, document_id, sku_1c, warehouse_id, quantity, operation_type, optional customer_id |
| Остаток | sku_1c, warehouse_id, as_of, on_hand, reserved либо ready-to-use free_stock, источник |
| Поставка в пути | shipment_id, sku_1c, warehouse_id, quantity, expected_date, unit |
| Наличие | sku_1c, warehouse_id, start_date, end_date, available/stockout, provenance |
| Политика поставщика/категории | lead_time_days, review_period_days, safety_days, growth_assumption, ограничения закупки |
| Результат | recommended_qty, final_qty, urgency, status, факторы расчёта, исключённые операции, допущения, source_refs |

Коды храним строками: ведущие нули и суффиксы значимы. Справочник соответствия артикулу поставщика связываем по коду 1С. Отдельно валидируем конфликты и единицы. Категория должна влиять на согласованную политику, например запас в днях; значения политики — видимые настройки, не выдуманные правила компании.

## 6. Расчётный алгоритм

Все параметры ниже — проектируемая методология. Их качество и пороги потребуется проверить.

### 6.1. Очистка и выбор области

Выбираем дату расчёта, склад, поставщика/категорию и период обучения. Сохраняем оригинальные строки. Нормализуем даты, коды, числовые значения, типы операций. Отрицательные значения анализируем как возможные возвраты/корректировки; не превращаем их в продажи через модуль.

Не смешиваем остатки всех складов с продажами одного. Для текущей сентябрьской выгрузки тренд сначала оцениваем по полным месяцам до августа 2026 включительно. Если используем сентябрь, учитываем фактическую длину наблюдения. Дату отчёта показываем в интерфейсе.

### 6.2. Исключение разовых продаж

Агрегируем положительные продажи по SKU + накладной; при наличии `customer_id` также проверяем сумму покупок клиента за день/неделю, чтобы дробление одного заказа на документы не обходило фильтр.

Оцениваем нетипичный размер относительно сопоставимой истории SKU и сезонного фона. Начальный кандидат — верхний modified Z-score на основе медианы и MAD с порогом 3.5; это признак возможной аномалии, а не доказательство разовой природы. Метод описан NIST: https://www.itl.nist.gov/div898/handbook/eda/section3/eda35h.htm.

Нужны отдельные ветки для MAD=0, короткой истории и редкого спроса: настраиваемый порог относительно типичного положительного заказа и статус ручной проверки. Не использовать медиану всех дней с нулями как единственный прогноз для редких продаж.

Сравниваем всплеск с повторяемостью заказов, общей динамикой и сезонным паттерном. Устойчивый рост нескольких периодов не удаляем как единичный выброс. Подтверждённый разовый заказ исключаем из обучающего ряда регулярного спроса, но сохраняем в фактических продажах и движении запаса. Для дневного всплеска с регулярными и разовыми заказами исключаем конкретные операции, не весь день. Показываем причину и возможность пересмотра.

### 6.3. Компенсация stockout

При подтверждённых днях отсутствия оцениваем нормальную скорость спроса по сопоставимым дням наличия, с сезонной поправкой. Пример: 200 единиц за 20 дней наличия в 30-дневном периоде → 10 в день → оценка 100 упущенных единиц и 300 полного спроса. Это демонстрационная арифметика при постоянном спросе, не измерение фактических потерянных продаж.

При нуле дней наличия нет основания делить на ноль: используем обоснованную историю/профиль или статус недостатка данных. Если календаря наличия нет, не выдаём нулевой остаток на начало месяца за stockout всего месяца. Приближённый сценарий допускается только с явной маркировкой и выбранными пользователем периодами.

### 6.4. Сезонность и рост

Строим полный временной ряд регулярного спроса в пределах подтверждённого покрытия данных. Очищаем разовые события, добавляем оценку упущенного спроса, затем оцениваем сезонность и тренд. Пропуски за пределами покрытия не заполняем нулями.

Для SKU с достаточной историей используем собственный сезонный профиль; при слабой истории — профиль категории или поставщика с указанием происхождения. Поставленные таблицы сезонности учитываем как внешний профиль/ориентир, но не применяем повторно поверх того же сезонного эффекта. Для расчёта базовой скорости снимаем сезонность, для прогнозного месяца возвращаем её.

Устойчивый рост оцениваем по нескольким завершённым периодам после снятия сезонности. Внешний прогноз прироста делаем отдельным настройочным источником: выбираем «исторический тренд», «прогноз менеджера» или явно дополнительную корректировку. Одно и то же увеличение не учитываем дважды. Для нового/редкого товара показываем ограниченность истории.

Прогноз по дням горизонта: `d(t) = base_daily_rate × season(t) × trend(t) × additional_growth(t)`. Каждый множитель положителен или нулевой и имеет определённый смысл; процент роста g преобразуем в `1 + g`. Политику допустимых значений валидируем.

### 6.5. Рекомендация заказа

```text
H = lead_time_days + review_period_days
D_H = сумма прогнозного спроса по дням горизонта H
S = прогнозный спрос за safety_days согласно политике категории
A = свободный остаток в выбранной области на дату расчёта
O_H = подтверждённые поставки, прибывающие до конца горизонта H
Q_raw = max(0, D_H + S - A - O_H)
```

Если есть MOQ и кратность в одной единице: при `Q_raw = 0` заказ равен 0; иначе `Q = ceil(max(Q_raw, MOQ) / pack_multiple) × pack_multiple`. MOQ и кратность — разные поля. Перед округлением переводим единицы закупки и хранения по подтверждённому коэффициенту. Некорректное MOQ не заменяем молча единицей.

Отдельно строим прогноз остатка по датам поступлений. Поставка после ожидаемого дефицита может уменьшать общий заказ, но не устраняет ранний дефицит; показываем его и дату. Не вычитаем весь транзит без учёта дат. Уже свободный остаток повторно не уменьшаем на резерв.

Для объяснения строки показываем: базовый спрос, сезонный/ростовой вклад, компенсацию отсутствия, исключённые события, горизонт, страховой запас, остаток, учтённый транзит и округление.

## 7. Интерфейс MVP

1. **Загрузка и качество данных.** Выбор поставщика, загрузка XLSX/набора, дата отчёта, сопоставленные SKU, пропущенные источники и ошибки. Обязательная настройка отсутствующих параметров.
2. **Рекомендации.** Группировка по поставщику, фильтры по категории/срочности/статусу. Колонки: код, название, остаток, в пути, прогноз, рекомендуемое количество, исправленное количество, причина.
3. **Карточка SKU.** История и очищенный спрос, отмеченные всплески, прогноз, расчёт количества и допущения. В интерфейсе может быть боковая панель, не отдельная страница.
4. **Проверка и экспорт.** Ручные изменения с причиной, утверждение конкретной версии расчёта, скачивание CSV/XLSX по поставщику. Новый расчёт снимает прежнее утверждение. Формат для 1С уточнить; до этого экспорт называем таблицей заказа, не готовой интеграцией.

Не включаем в первые пять часов роли/регистрацию, чат как основной экран, отдельный AI-сервис, автоматическую рассылку и интеграцию с живой 1С.

## 9. Проверки, которые определяют готовность

- Обычный товар: ручной расчёт совпадает с системой.
- Разовый заказ 100× обычного: записан в журнал исключений; регулярный прогноз меняется не более согласованного допуска. Начальный инженерный ориентир для контролируемого теста — 5%, это не критерий организатора. Проверяем до округления и отдельно после него.
- Один клиент дробит крупный заказ на несколько накладных: клиентский агрегат всё равно выявляет событие.
- Повторяющиеся крупные покупки и устойчивый рост не исключаются автоматически как разовые.
- Сезонный ряд: прогноз воспроизводит следующий сезонный пик.
- Stockout: известные дни отсутствия увеличивают оценку полного спроса; неизвестные периоды не порождают фиктивную компенсацию.
- Больше свободного остатка или своевременного транзита — меньше неокруглённый заказ в тесте без насыщения нулём. Поздний транзит не маскирует ранний дефицит.
- Категория и прогноз прироста реально изменяют расчёт через явно заданные политики.
- Возвраты, нулевая история, MAD=0, новый товар, неизвестная категория, ошибка MOQ, дубликат и пропуск ключевого источника дают определённый результат/статус.
- Экспорт совпадает с утверждённой версией и ручными корректировками; сам ничего не отправляет.
- Контроль повторного импорта исключает двойной учёт данных. Один ввод с одной конфигурацией даёт одинаковый результат.

Для оценки качества прогноза при наличии сопоставимых данных используем последовательное тестирование на завершённых месяцах: обучаемся только на более ранних данных, сравниваем с простым средним/сезонным прошлогодним прогнозом. Считаем MAE/WAPE и систематическое смещение только на наблюдаемых сопоставимых периодах. При нулевой сумме факта WAPE не определён. Настройки, сезонность и тренд для каждого тестового среза не используют будущие данные.

Снижение заказа после исключения всплеска не равно доказанной экономии. Денежный эффект и сокращение дефицита можно заявлять лишь после отдельной проверки с ценами, истинным спросом и сопоставимыми условиями.

Реальный импорт даёт PARTIAL: отсутствующие бизнес-правила и подтверждения не подменяются фактами. Следующие этапы — уточнить данные с Altynbek, проверить расчёт на согласованном реальном наборе и подключить IEK. Исправленные исходные факты пока загружаются новым JSON; отдельного редактора нет. Сводки месяцев сохраняются и используются для отчёта о расхождениях; объединение их с детализацией для прогноза требует подтверждения области источников. Backtest остаётся отдельным этапом. PostgreSQL добавляется после проверки сквозного сценария, по договорённости с Rajan.
