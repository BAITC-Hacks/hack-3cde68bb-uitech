# Контрольные сценарии API

Все данные в `fixtures/contract/` синтетические. Категории и параметры не описывают реальные правила Электрокомплекта. Все 17 сценариев проходят в `backend/src/test/java/kz/uitech/CalculationTest.java`; API дополнительно проверяет запрет утверждения неполных данных, версии, ручные изменения и экспорт. Команда: из backend `mvn verify`. Это проверка заданных сценариев, не оценка точности на данных компании.

## Базовый пример

30 дней июня: ежедневно продаётся 10 штук, товар всё время в наличии. На начало 1 июля свободный остаток 40. Подтверждённая поставка 20 штук поступает 8 июля. Срок нового заказа 7 дней, период между заказами 7, страховой запас 7 дней. Сезонность 1, ручной прирост 0%, кратность 10 штук.

Расчёт: `10 × (7 + 7) + 10 × 7 − 40 − 20 = 150`. Заказ — 150 штук. Имеющегося остатка хватает на 1–4 июля; 5 июля возникает дефицит до поступления транзита. Новая рекомендация ещё не считается размещённой поставкой.

## Соответствие ТЗ

- Все источники влияют: 01–05, 11–12.
- Сезонность и устойчивый рост: 06, 10. Сценарий 06 проверяет применение предоставленного профиля. Тест `estimateSeasonNeedsTwoCompleteCycles` отдельно проверяет блокировку короткой истории и расчёт по двум полным циклам на постоянном ряде; он не доказывает качество оценки сезонности на реальных SKU.
- Компенсация отсутствия: 07; тесты `unknownAvailabilityNeverMeansZeroDemand` и `assumedAvailabilityIsDisclosed` проверяют неизвестное наличие и раскрытие явного допущения.
- Крупные разовые заказы и один клиент: 08–09; 16 защищает от чрезмерного исключения регулярных заказов.
- Группировка и объяснение: 15 и наличие числовой расшифровки во всех готовых строках.

## Порядок применения

1. Загрузить `dataset` из fixture через `POST /api/v1/datasets`.
2. В `calculation` добавить полученный `dataset_id`, отправить через `POST /api/v1/calculations`.
3. Найти строки по `product_id`, не полагаться на порядок массива.
4. Числовые ожидания сопоставить с полями строки или `factors`; для арифметики без округления допуск 0.000001, итоговые кратности и коды сравнивать точно.
5. Для 08–09 сначала выполнить 01 с тем же методом и параметрами. Проверить журнал аномалий и сохранение обычной продажи.
6. Для утверждения отдельно проверить revision: изменение количества сбрасывает approval, устаревшая revision даёт 409, выгрузка до утверждения даёт 409, пустой обязательный ввод блокирует утверждение.
7. Файл экспорта должен содержать утверждённые окончательные количества только выбранного поставщика. Сетевых отправок нет.

Поле `assertions` поясняет ожидаемое поведение; автоматические проверки реализованы явно в `CalculationTest`, текст сам по себе не исполняется. `preserve_document_ids` должны оставаться в регулярном спросе; `excluded_document_ids` — присутствовать в журнале исключений. Пустой список excluded в сценарии роста означает отсутствие исключённых продаж.

Воспроизведение файлов: `python tools/generate_contract_fixtures.py`. Скрипт только создаёт тестовые данные и не реализует прогнозирование.
