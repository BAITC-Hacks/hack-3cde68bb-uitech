# SupplyMind — пополнение склада

HackAlem AI, задача «Электрокомплекта»: рекомендации заказов поставщикам с учётом регулярного спроса, сезонности, роста, остатков, транзита и периодов отсутствия товара.

Команда: Uitech.

## Текущее состояние

Работают Java backend и отдельный frontend: импорт шести файлов Systeme Electric или IEK, расчёт потребности, журнал исключённых продаж, прогноз дефицита, группировка по поставщикам, ручная корректировка, утверждение версии и CSV-экспорт. В интерфейсе есть графики, поиск, фильтры, отчёт качества и семь демо-сценариев.

Реальные данные импортируются со статусом `PARTIAL`: для обоснованного заказа нужно уточнить область остатков и транзита, наличие товара, правила закупки и полноту продаж. Полностью работающий сценарий можно проверить на явно обозначенных синтетических данных без личных аккаунтов.

## Запуск

Нужны JDK 17, Maven 3.9+ и Node.js 22.12+ (проверено на 22.15.1). Для вспомогательных скриптов — Python 3.11+. Первая сборка скачивает зависимости из Maven Central и npm; последующие расчёты не требуют внешней сети.

Из корня этого репозитория:

```powershell
cd backend
mvn clean verify
java -Xmx768m -jar target/replenishment-0.1.0.jar
```

API: `http://127.0.0.1:8080/api/v1`, проверка — `GET /health`. Перед пересборкой JAR остановите запущенный backend через Ctrl+C.

В другом терминале, из корня репозитория:

```powershell
cd frontend
npm ci
npm run dev
```

Откройте **http://127.0.0.1:5173**. Vite проксирует `/api` на backend. Если backend работает на другом порту, перед запуском frontend задайте `$env:BACKEND_URL = 'http://127.0.0.1:8090'`. Продакшен-сборка: `npm run build`; её локальная проверка: `npm run preview`, адрес http://127.0.0.1:4173 (backend должен работать). Это локальный preview, не production hosting.

### Проверка через интерфейс

1. Нажмите **Демо-сценарии → Заказы двум поставщикам**. Синтетические данные явно помечены; числа рассчитывает backend.
2. Откройте товар: видны формула, MOQ/кратность, графики спроса и наличия. В сценарии «Разовая крупная продажа» дополнительно виден журнал исключённого всплеска.
3. Измените количество и укажите причину. Например, 150 → 160 шт. при кратности 10.
4. Утвердите заказ, указав имя проверившего и подтвердив предупреждения, если они есть. Скачайте CSV выбранного поставщика.
5. Повторная правка снимает утверждение. При неизвестном остатке утверждение и экспорт недоступны.

Уже сохранённые наборы доступны в **Источники данных**. Кнопка **Загрузить данные** принимает шесть XLSX выбранного поставщика (Systeme Electric / IEK) либо нормализованный JSON/контрольный пример. В интерфейсе ZIP сначала нужно распаковать. Реальный набор не получает вымышленных сроков поставки, MOQ, коэффициентов единиц и календаря наличия: данные нужно уточнить перед утверждением. Исправление исходных фактов пока выполняется через новый нормализованный JSON; отдельного редактора этих фактов ещё нет.

В браузере сохраняется только ID последнего открытого расчёта, чтобы восстановить его после обновления страницы. Наборы и расчёты остаются на backend в `.local`; реальные данные в frontend bundle не включаются.

В другом терминале, из корня репозитория:

```powershell
python tools/demo_backend.py --approve
```

Команда загружает синтетический пример, рассчитывает заказ 150 шт., утверждает его от имени тестового пользователя и сохраняет JSON/CSV в `.local/demo/`. Без `--approve` результат остаётся черновиком. Другой сценарий: `python tools/demo_backend.py --fixture 08_one_off_order`.

Переменные окружения: `PORT` (8080), `UITECH_BIND_ADDRESS` (127.0.0.1), `UITECH_DATA_DIR` (`../.local/backend-data` относительно каталога запуска). Для неизменного пути при запуске из других каталогов задайте `UITECH_DATA_DIR` абсолютным путём. Хранилище — локальные JSON-файлы, один процесс backend; полноценные пользователи, роли и многопроцессная база данных пока не реализованы.

## Импорт Systeme Electric и IEK

При работающем сервере, из корня репозитория:

```powershell
python tools/import_supplier.py "C:\Users\User\Downloads\Systeme electric.zip" --supplier SYSTEME
python tools/import_supplier.py "C:\Users\User\Downloads\IEK.zip" --supplier IEK
```

Скрипт читает архив в памяти и отправляет шесть XLSX через multipart API. Исходные файлы не меняются. API принимает XLSX: до 15 МБ на файл и 40 МБ на запрос. Серверный ZIP-импорт не реализован.

На предоставленном архиве получены: 724 товара, 76 997 принятых строк продаж, 497 снимков остатка, 7 ненулевых поставок, 18 282 месячных значения продаж и 23 133 значения остатков. Объединение справочников включает товары, отсутствующие в отдельных источниках. 315 операций детализации вынесены в сообщения карантина; количество не меняется через модуль. Полный нормализованный набор и все замечания доступны через `GET /datasets/{id}/data`; краткий отчёт ограничен первыми 200 замечаниями.

IEK: 3 185 товаров, 171 470 принятых строк продаж, 81 279 месячных значений продаж, 94 149 значений начальных остатков. Отдельно сохранены 306 записей партий (`reported_inbound`) и 1 938 строк ограничений отгрузки (`reported_purchase_rules`). 133 операции — в карантине; 15 ошибок MOQ и дубликаты сохранены с замечаниями. Актуальных остатков IEK нет; начальные остатки месяца их не заменяют. Сроки «поступление до» остаются предельными датами, количества партий не вычитаются из заказа до подтверждения единиц и склада. Нормализованный транзит пока пустой — это не утверждение об отсутствии товара в пути. В отчёте качества можно раскрыть исходные партии и правила.

После уточнений можно получить нормализованный JSON, исправить подтверждённые поля с указанием ручного источника и создать новый dataset через `POST /datasets`. Старый набор сохраняется. Допущения, поддерживаемые расчётом, описаны в контракте. Неизвестный остаток, MOQ или коэффициент единиц не заменяются нулём/единицей. Помесячные остатки сохраняются для сверки и не превращаются в вымышленные даты stockout. Для интерфейса `GET /datasets/{id}/review` возвращает справочники и качество без полной истории продаж; `/data` сохраняет полный набор.

## Метод расчёта

Продажи агрегируются по документу и по клиенту за день. Детектор использует медиану/MAD, сезонную нормализацию и повторяемость крупных покупок по неделям. Исключения видны в результате; при отсутствии ID клиента проверяются только документы.

Очищенный спрос делится на подтверждённые дни наличия. Упущенный спрос при stockout оценивается отдельно. Применяется предоставленная сезонность либо оценка по двум полным годовым циклам, затем ручной прирост либо линейный тренд минимум по трём полным месяцам. Потребность: прогноз на срок поставки и период пересмотра + страховой запас − свободный остаток − своевременный транзит. Итог переводится в единицы закупки и округляется по MOQ/кратности.

Каждая позиция содержит факторы расчёта, дневную историю, прогноз и объяснение. Утверждение требует подтверждения предупреждений. Ручная правка увеличивает версию и отменяет прежнее утверждение; экспорт доступен только для актуальной утверждённой версии. Отправки поставщикам нет.

## Проверки и зависимости

`mvn clean verify` запускает автоматические тесты: 17 контрольных сценариев, обработка неполных данных, API, версии, экспорт, чтение XLSX. Тесты реальных архивов по умолчанию пропускаются; включить их из `backend`:

```powershell
mvn verify "-DargLine=-Xmx512m" "-Duitech.systemeZip=C:\Users\User\Downloads\Systeme electric.zip" "-Duitech.iekZip=C:\Users\User\Downloads\IEK.zip"
```

На 23.09.2026 `verify` с обоими реальными архивами и `-DargLine=-Xmx512m`: 36 тестов, 0 ошибок, 0 пропусков. Без архивов выполняются 34 проверки, две пропускаются. Ограничение heap предотвращает чрезмерное выделение памяти JVM при одновременно открытых IDE и браузере. Проверены сборка JAR, HTTP-сценарий расчёт → утверждение → CSV, multipart-импорт и повторное сохранение без дублирования. Это проверка реализации, а не доказательство точности прогноза или экономии компании. Исторический backtest и сравнение с работой менеджера ещё не выполнены.

Frontend проверяется командами `npm run build` и `npm run test:e2e` из `frontend`. Для E2E должны работать backend и frontend; по умолчанию используется установленный Microsoft Edge. Другой браузер: `$env:PLAYWRIGHT_CHANNEL = 'chrome'`. Тест реального XLSX-импорта включается переменной `UITECH_XLSX_DIR`, указывающей на каталог с шестью распакованными файлами Systeme. Для IEK задайте `UITECH_IEK_XLSX_DIR` с его шестью файлами. Без архивов запускаются четыре проверки, две пропускаются. Набор E2E включает шесть сценариев, в том числе настоящий multipart-импорт обоих поставщиков. Артефакты — `frontend/test-results/`, в Git не попадают.

Основные зависимости: Java 17, Spring Boot 3.5.16 (Apache-2.0), Apache POI 5.5.1 (Apache-2.0), Jackson через Spring Boot (Apache-2.0), JUnit Jupiter для тестов (EPL-2.0); React 19.3.0 (MIT), Vite 8.3.0 (MIT), TypeScript 7.0.2 (Apache-2.0), Playwright 1.63.0 для E2E (Apache-2.0), Prettier для форматирования (MIT). Версии зафиксированы в `backend/pom.xml`, BOM Spring Boot и `frontend/package-lock.json`; транзитивный состав показывает `mvn dependency:tree` и `npm ls`. Документация: [React](https://react.dev/learn), [Vite](https://vite.dev/guide/). LLM/API модели в текущем расчёте не используются. Реальные материалы предоставлены организатором; в Git их нет. Контрольные примеры созданы командой и полностью синтетические.

Последняя проверка: все шесть E2E прошли в Edge, включая повторный импорт IEK при уже загруженных обоих наборах; backend запущен с `-Xmx512m`. XLSX читается SAX из временного файла в режиме READ, чтобы POI не распаковывал весь архив в heap; временный файл удаляется после чтения. Сериализация локального dataset и подсчёт hash выполняются потоково. Для IEK ответ `/review` занимает 3 893 719 байт против 96 877 642 байт полного JSON; исходные данные сохранены полностью.
